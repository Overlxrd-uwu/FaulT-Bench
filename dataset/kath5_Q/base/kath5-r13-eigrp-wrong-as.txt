Scenario: kath5-r13-eigrp-wrong-as
Topology: Kath5
Fault family: EIGRP AS mismatch
==================================================

[PROMPT-TO-AGENT]
After a "rollback" on r13, R11 reports it lost an EIGRP
neighbor and 113.1.x.x routes disappeared from R11's topology
table. R13 reports EIGRP is running and its config looks valid.
What changed?

[INJECTION]
device: r13
action: change EIGRP AS from 100 to 300 (a value R11 doesn't speak)
cmd: |
  vtysh -c "configure terminal" \
        -c "no router eigrp 100" \
        -c "router eigrp 300" \
        -c "network 103.0.0.0/8" \
        -c "network 113.1.1.0/24" \
        -c "network 113.1.2.0/24" \
        -c "network 113.1.3.0/24" \
        -c "network 113.1.4.0/24" \
        -c "exit" -c "exit"

[POST-INJECT-CHECK]
r13  vtysh -c "show running-config" | grep -c "router eigrp 300"  => expect 1
r11  vtysh -c "show ip eigrp neighbor" | grep -c 103.1.1.2 => expect 0

[GROUND-TRUTH]
Affected component: r13 EIGRP AS number
Mechanism: EIGRP requires both ends of an adjacency to share
  the same AS. R11 runs AS 100 (covering both R12 and R13
  sides per the collapsed-single-AS fix from earlier). R13
  was reconfigured to AS 300. Hello packets carry the AS,
  the mismatch is detected, and the adjacency never forms.
  R11 stops seeing 113.1.x routes, and R13 stops seeing
  102.x / 112.x / 120.x routes from R12 via R11.
Localization: r13
Root cause: EIGRP AS mismatch (R13 in AS 300, R11/R12 in AS 100)
Fix: re-configure r13 to AS 100

[FIX]
re-configure r13 to AS 100

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm R11 has lost the EIGRP neighbor at 103.1.1.2
   (R13) and that 113.1.x routes are absent from R11's topology table;
   check that R12's adjacency with R11 is unaffected (partial neighbor loss).
2. Check EIGRP neighbor state on R11: `show ip eigrp neighbor` -- R13 should
   not appear; confirm EIGRP process on R13 is running (`show running-config`
   on R13 shows `router eigrp` is active).
3. Compare the EIGRP AS number on both ends: R11 runs AS 100; inspect R13's
   running config to find `router eigrp 300` -- the mismatch is the cause.
4. Explain the adjacency failure mechanism: EIGRP Hello packets carry the
   AS number; when the two ends disagree, the adjacency never forms and no
   routes are exchanged in either direction.
5. Localize to the lowest-layer root cause: wrong AS number (300 vs 100)
   in R13's EIGRP configuration; rule out a link failure or interface issue.
