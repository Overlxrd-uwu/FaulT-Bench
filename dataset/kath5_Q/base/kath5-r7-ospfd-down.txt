==================================================
Scenario: kath5-r7-ospfd-down
Topology: Kath5
Fault family: routing daemon down (ABR isolates an area)
==================================================

[PROMPT-TO-AGENT]
After a change on r7, routes for 17.x.x.x (R7 loopbacks),
67.0.0.0/8 (R7-R6 link), and 70.0.0.0/8 (R7 LAN) disappeared
from r1's routing table. R7 used to have an OSPF adjacency
with R6. Identify what's wrong.

[INJECTION]
device: r7
action: kill ospfd
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
r7  pgrep ospfd                                          => expect empty
r6  vtysh -c "show ip ospf neighbor" | grep 67.1.1.2     => expect empty
r1  vtysh -c "show ip route" | grep -c "17\.\|70\."      => expect 0

[GROUND-TRUTH]
Affected component: r7 ospfd daemon
Mechanism: r7 owns the 17.1.{1..4}.0/24 loopback range, the
  70.0.0.0/8 LAN, and forms the only OSPF adjacency with r6
  over 67.0.0.0/8. With its ospfd dead, r6 ages out r7's
  prefixes and they propagate as withdrawals through area 1
  and the backbone. r1 loses visibility into the r7 region.
Localization: r7
Root cause: ospfd not running on r7
Fix: `/etc/init.d/frr restart` on r7

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on r7" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on r7

[DIAGNOSTIC-PROCESS]
1. Scope which prefixes are unreachable: confirm 17.x.x.x (loopbacks),
   67.0.0.0/8 (R7-R6 link), and 70.0.0.0/8 (R7 LAN) are absent from
   R1's RIB.
2. Inspect R6's OSPF neighbor state: `show ip ospf neighbor` on R6 -- the
   adjacency to 67.1.1.2 (R7) should be gone; this indicates R7's OSPF
   is the source of the failure.
3. Check the daemon/process state on R7: `pgrep ospfd` on R7 returns empty,
   confirming ospfd is not running; without ospfd R7 cannot form or maintain
   an OSPF adjacency.
4. Explain the withdrawal chain: with R7's ospfd dead, R6 ages out R7's
   LSAs; those prefixes propagate as withdrawals through area 1 and the
   backbone, reaching R1.
5. Localize to the lowest-layer root cause: ospfd is not running on R7;
   rule out a link failure between R6 and R7 or an OSPF configuration
   change on either router.
