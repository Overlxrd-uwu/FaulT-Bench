==================================================
Scenario: kath5-r6-ospfd-down
Topology: Kath5
Fault family: routing daemon down (intermediate router)
==================================================

[PROMPT-TO-AGENT]
After an upgrade attempt on r6, all routes for the r7 region
(67.0.0.0/8, 17.x.x.x, 70.0.0.0/8) became unreachable from
r1, even though r7 itself is still up and its ospfd is running.
What happened to the connectivity between r6 and the rest of
the backbone?

[INJECTION]
device: r6
action: kill ospfd
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
r6  pgrep ospfd                                          => expect empty
r7  vtysh -c "show ip ospf neighbor" | grep 16.1.4.1     => expect empty
r1  vtysh -c "show ip route" | grep -c "67.0.0.0"        => expect 0

[GROUND-TRUTH]
Affected component: r6 ospfd
Mechanism: r6 is the area 1 transit router connecting r7
  (and its 67.0.0.0/8, 17.x, 70.x) to the rest of area 1
  and onward to the backbone via r4. Without r6's ospfd,
  r7 has nobody to peer with — its routes never reach the
  backbone. From r1's perspective, all r7-region prefixes
  withdraw.
Localization: r6
Root cause: ospfd not running on r6
Fix: `/etc/init.d/frr restart` on r6

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on r6" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on r6

[DIAGNOSTIC-PROCESS]
1. Scope which prefixes are unreachable: confirm 67.0.0.0/8, 17.x.x.x, and
   70.0.0.0/8 are absent from R1's RIB; note R7 is reported up.
2. Inspect R7's OSPF neighbor state: `show ip ospf neighbor` on R7 -- the
   adjacency to 16.1.4.1 (R6) should be gone, indicating R6 is the transit
   failure, not R7 itself.
3. Check the routing table on R6: `show ip route` on R6 -- if ospfd is dead,
   R6 will have no OSPF routes; confirm ospfd process state with `pgrep ospfd`.
4. Check the daemon/process state on R6: `pgrep ospfd` returns empty,
   confirming ospfd is not running on R6; no adjacency can form so R7's
   routes never reach the backbone.
5. Localize to the lowest-layer root cause: ospfd is not running on R6;
   rule out a link failure between R6 and R7 or an OSPF configuration
   change on R7.
