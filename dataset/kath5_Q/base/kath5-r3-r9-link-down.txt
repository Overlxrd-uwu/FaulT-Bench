==================================================
Scenario: kath5-r3-r9-link-down
Topology: Kath5
Fault family: WAN link cut (backbone)
==================================================

[PROMPT-TO-AGENT]
After a maintenance window, routes for 19.0.0.0/8, 39.0.0.0/8,
and 90.0.0.0/8 became less stable in r1's RIB. r3 reports
losing an OSPF neighbor. Find the affected link.

[INJECTION]
device: r3
action: bring down the link toward r9
cmd: ip link set eth0 down

[POST-INJECT-CHECK]
r3  ip -br link show eth0 | grep -c UP                   => expect 0
r1  vtysh -c "show ip route" | grep -c "90.0.0.0"        => expect 0

[GROUND-TRUTH]
Affected component: r3 link toward r9
Mechanism: r3 is r9's ONLY backbone neighbor (r9's other
  interface is a stub LAN). r9 owns the 19.0.0.0/8 and
  90.0.0.0/8 prefixes. With the link down, the adjacency
  drops and r9 is fully isolated -- its prefixes disappear
  from the backbone RIBs.
Localization: r3 (eth toward r9)
Root cause: backbone link r3<->r9 is down
Fix: bring the link back up

[FIX]
bring the link back up

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm R1 has lost routes for 19.0.0.0/8, 39.0.0.0/8,
   and 90.0.0.0/8; note R3 is reporting a dropped OSPF neighbor.
2. Check interface/link state on R3: inspect the interface facing R9 to
   confirm it is operationally down (L1/L2 failure), not a configuration
   change.
3. Check the OSPF adjacency consequence: `show ip ospf neighbor` on R3
   confirms the Full adjacency to R9 has dropped as a direct result of the
   link failure, not from an OSPF configuration change.
4. Correlate to prefix loss: R9 owns 19.0.0.0/8 and 90.0.0.0/8; with the
   adjacency gone R3 can no longer reach R9's LSAs, so those prefixes
   withdraw from the backbone and disappear from R1's RIB.
5. Localize to the lowest-layer root cause: physical/logical link R3<->R9
   (eth toward r9) is down; rule out an OSPF misconfiguration on either R3
   or R9.

must-recognize-prefix-loss
