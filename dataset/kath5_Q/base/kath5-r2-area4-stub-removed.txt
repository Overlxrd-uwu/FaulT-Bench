==================================================
Scenario: kath5-r2-area4-stub-removed
Topology: Kath5
Fault family: OSPF area stub config removed
==================================================

[PROMPT-TO-AGENT]
After a config change on r2, r10 (which is in area 4) lost its
OSPF adjacency to r2 and its routing table collapsed -- every
route beyond area 4 vanished from r10's RIB and hosts behind
r10 lost the backbone. r2 reports area 4 stub configuration is
no longer active. What's wrong?

[INJECTION]
device: r2
action: remove `area 4 stub` from OSPF config
cmd: |
  vtysh -c "configure terminal" \
        -c "router ospf" \
        -c "no area 4 stub" \
        -c "exit" -c "exit"

[POST-INJECT-CHECK]
r2   vtysh -c "show running-config" | grep -c "area 4 stub"   => expect 0
r10  vtysh -c "show ip ospf neighbor" | grep -c Full           => expect 0

[GROUND-TRUTH]
Affected component: r2 OSPF area 4 stub designation
Mechanism: Area 4 was originally configured as a stub on BOTH
  r2 (ABR) and r10 (internal). The stub flag (Hello E-bit)
  must MATCH between neighbors: when r2 drops `area 4 stub`,
  r10 (still stub) rejects r2's Hellos, and after the dead
  interval (~40 s) the r2<->r10 adjacency DROPS. r2 is r10's
  ONLY OSPF neighbor, so r10 is isolated from the OSPF domain:
  its OSPF RIB collapses to intra-area entries (lab-verified
  2026-07-12: 61 -> 13 `show ip route ospf` lines, neighbor
  table empty, zero external LSAs -- NOT an external-flood
  RIB bloat).
Localization: r2 (the ABR is responsible for area type config)
Root cause: `area 4 stub` missing from r2's OSPF process
Fix: `vtysh -c "router ospf" -c "area 4 stub"` on r2

[FIX]
`vtysh -c "router ospf" -c "area 4 stub"` on r2

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm R10 lost its OSPF adjacency (empty neighbor
   table) and its OSPF routes beyond area 4; note R10 is in area 4 and its
   only neighbor is R2 (the ABR).
2. Check OSPF state on R10: `show ip ospf neighbor` is empty while R10's own
   interface and stub configuration are unchanged -- the failure is at Hello/
   adjacency level, not a local R10 change.
3. Inspect the ABR configuration: examine R2's OSPF config (`show
   running-config` on r2 | grep "area 4") -- confirm `area 4 stub` is
   missing; R2 is the ABR responsible for the area 4 stub designation.
4. Explain the stub-mismatch mechanism: the Hello E-bit must match on both
   ends; when R2 drops the stub flag, R10 rejects its Hellos and the adjacency
   dies after the dead interval -- isolating area 4 from the backbone.
5. Localize to the lowest-layer root cause: missing `area 4 stub` on R2
   (the ABR); rule out a link failure or an internal R10 config change.
