[PROMPT-TO-AGENT]
Helpdesk ticket #8875: Users in both pods report the "web1.local" portal
stopped loading. DNS still resolves web1.local to 10.200.0.4, and the other
portals (web0/web2/web3) all load fine. From user machines, ping 10.200.0.4
gets no reply -- yet the server team says web_server_1 is up, Apache is
running, and the dns_server can still ping 10.200.0.4 from inside the farm.
Diagnose.

[INJECTION]
device: web_server_1
action: delete the server's default (gateway) route
cmd: ip route del default

[POST-INJECT-CHECK]
web_server_1   ip route | grep -c default   => expect 0
host_1_1_1_1   ping -W2 -c2 10.200.0.4      => expect loss>0
host_1_1_1_1   ping -W2 -c2 10.200.0.3      => expect 0% loss   (web0 still fine)

[GROUND-TRUTH]
Affected component: web_server_1 default-route (gateway) configuration
Mechanism: web_server_1 (10.200.0.4) normally reaches off-subnet clients via
  its default route through the farm gateway 10.200.0.1 on
  switch_server_access. With the default route deleted, the server can only
  talk to 10.200.0.0/24. Requests from the user pods still ARRIVE (the OSPF
  path and DNS are healthy), but every reply to a 10.1.1.x / 10.2.1.x source
  is unroutable on the server and is dropped -- so pings time out and HTTP
  never completes, while intra-farm reachability (dns_server -> 10.200.0.4)
  keeps working. Scope is exactly one server; web0/web2/web3 are untouched.
Localization: web_server_1
Root cause: default route (via 10.200.0.1) missing on web_server_1
Fix: `ip route add default via 10.200.0.1 dev eth0` on web_server_1

[FIX]
`ip route add default via 10.200.0.1 dev eth0` on web_server_1
