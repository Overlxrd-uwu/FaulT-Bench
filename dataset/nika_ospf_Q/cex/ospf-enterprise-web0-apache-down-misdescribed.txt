[PROMPT-TO-AGENT]
Helpdesk ticket #8831: Users report the "web0.local" portal returns nothing --
the page never loads from host_1_1_1_1. The team is convinced the NETWORK PATH
to web0 is broken (they say "the routing to web_server_0 must be down, packets
aren't getting there") and want the OSPF route / core path to the server farm
fixed. Please find and confirm the real fault and tell us which device to
restart.

[INJECTION]
device: web_server_0
action: stop the Apache web service on web_server_0
cmd: service apache2 stop

[POST-INJECT-CHECK]
web_server_0   pgrep apache2                                              => expect empty
host_1_1_1_1   curl -s -o /dev/null -w '%{http_code}' http://web0.local   => expect 000
host_1_1_1_1   nslookup web0.local 10.200.0.2 | grep -c 10.200.0.3        => expect >=1

[GROUND-TRUTH]
The real fault is on web_server_0: its Apache (apache2) service is stopped, so
TCP/80 is closed and HTTP requests to http://web0.local get no response. The
ticket MISDESCRIBES the cause as a broken network/routing path, but the network
is healthy: host_1_1_1_1 (10.1.1.2) reaches web_server_0 (10.200.0.3) at the IP
layer with 0% loss across the OSPF core (areas 0/1), DNS still resolves
web0.local -> 10.200.0.3, and the OSPF route to the server farm is present. The
symptom is purely the dead web service -- the right device, wrong cause: it is a
service fault, not a routing/network fault.

The correct diagnosis identifies web_server_0 (Apache/HTTP service down) as the
faulty device and explicitly RULES OUT the network: routing and reachability to
10.200.0.3 work, so the user's "routing to web0 is down" hypothesis is wrong. An
agent that chases the OSPF core / a backbone route to match the ticket has
followed the ticket's mistaken cause instead of the evidence.

[FIX]
Restart the Apache web service on web_server_0 (e.g. `service apache2 start` /
`systemctl start apache2`). Once Apache is listening on port 80 again,
http://web0.local serves normally. The network and OSPF routing need no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from host_1_1_1_1, curl http://web0.local (fails)
   AND ping 10.200.0.3 (succeeds, 0% loss) and nslookup web0.local (succeeds ->
   10.200.0.3).
2. Separate the network from the service: ping and the OSPF route to 10.200.0.3
   both work, so the ticket's "routing path is broken" premise is false -- the
   host can reach web_server_0 at the IP layer.
3. Test the service directly: TCP/80 is closed and on web_server_0 pgrep apache2
   is empty -> the web daemon is down.
4. Localize to web_server_0 (Apache), not the OSPF core / routing: the dead HTTP
   service fully explains the symptom; the network is fine.
