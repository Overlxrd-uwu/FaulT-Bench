==================================================
Scenario: ospf-enterprise-dns-named-down-misdescribed
Topology: ospf_enterprise_static
Fault family: service down (misdescribed ticket -- wrong cause)
==================================================

[PROMPT-TO-AGENT]
Helpdesk ticket #8843: Users report that internal names ("web0.local",
"web1.local") will not resolve from host_1_1_1_1. The team is convinced the
campus DNS server lost its network path -- they say "we can't reach the DNS
server anymore, the routing to 10.200.0.2 must be down" -- and want the OSPF
route / core path to the DNS server fixed. Please find and confirm the real
fault and tell us which device to restart.

[INJECTION]
device: dns_server
action: stop the BIND (named) DNS service on dns_server
cmd: pkill -9 named

[POST-INJECT-CHECK]
dns_server     pgrep named               => expect empty
host_1_1_1_1   ping -W2 -c2 10.200.0.3   => expect 0% loss

[GROUND-TRUTH]
The real fault is on dns_server: its BIND (named) service is stopped, so the
campus DNS no longer resolves names -- web0.local, web1.local and the other
*.local names fail to resolve, which is why the portals never load by name. The
ticket MISDESCRIBES the cause as a lost network path to the DNS server, but the
network is healthy: host_1_1_1_1 (10.1.1.2) reaches dns_server (10.200.0.2) at
the IP layer with 0% loss across the OSPF core (areas 0/1), and the OSPF route to
the server farm is present. The symptom is purely dead name resolution -- the
right device, wrong cause: it is a service fault on dns_server, not a
routing/network fault.

The correct diagnosis identifies dns_server (DNS/named service down) as the
faulty device and explicitly RULES OUT the network: the host reaches 10.200.0.2
by ping and the OSPF route to it is fine, so the user's "routing to the DNS
server is down" hypothesis is wrong. An agent that chases the OSPF core / a
backbone route to the server farm to match the ticket has followed the ticket's
mistaken cause instead of the evidence.

[FIX]
Restart the BIND DNS service on dns_server (e.g. `systemctl start named`). Once
named is resolving again, web0.local / web1.local resolve to their server IPs and
the portals load normally. The network and OSPF routing need no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from host_1_1_1_1, resolving web0.local /
   web1.local by name fails, but the DNS server itself is reachable by IP (ping
   10.200.0.2 succeeds, 0% loss).
2. Separate the network from the service: ping and the OSPF route to 10.200.0.2
   both work, so the ticket's "routing to the DNS server is down" premise is false
   -- the host can reach dns_server at the IP layer.
3. Test name resolution directly: queries to 10.200.0.2 do not resolve the *.local
   names; on dns_server, pgrep named is empty -> the DNS daemon is down.
4. Localize to dns_server (named), not the OSPF core / routing: the dead DNS
   service fully explains the symptom; the network is fine.

[SCORING-AXES]

must-identify-dns-down: identifies the DNS/named service on dns_server is stopped (names do not resolve), not a routing or network fault
bonus-rules-out-network: explicitly notes the network/OSPF path to 10.200.0.2 is healthy (ping/route succeed), rejecting the ticket's "routing to the DNS server is down" cause
