Scenario: ospf-enterprise-web0-apache-down-misdirected
Topology: ospf_enterprise_static
Fault family: service down (misdirected ticket)
==================================================

[PROMPT-TO-AGENT]
Helpdesk ticket #8830: Users report the "web0.local" portal returns nothing --
the page never loads from host_1_1_1_1. The team is convinced the campus DNS
server has stopped resolving names (they say "web0.local must not be resolving
anymore") and want the DNS server restarted. Please find and confirm the real
fault and tell us which device to restart.

[INJECTION]
device: web_server_0
action: stop the Apache web service on web_server_0
cmd: service apache2 stop

[POST-INJECT-CHECK]
web_server_0   pgrep apache2                                              => expect empty
host_1_1_1_1   curl -s -o /dev/null -w '%{http_code}' http://web0.local   => expect 000
host_1_1_1_1   nslookup web0.local 10.200.0.2 | grep -c 10.200.0.3        => expect >=1

[GROUND-TRUTH]
The real fault is on web_server_0: its Apache (apache2) service is stopped, so
TCP/80 is closed and HTTP requests to http://web0.local get no response. The
ticket MISDIRECTS to the DNS server, but DNS is healthy: dns_server (10.200.0.2)
still resolves web0.local -> 10.200.0.3 correctly, and host_1_1_1_1 reaches
web_server_0 (10.200.0.3) at the IP layer (ping succeeds). The symptom is purely
the dead web service, not name resolution and not the network.

The correct diagnosis identifies web_server_0 (Apache/HTTP service down) as the
faulty device and explicitly EXONERATES the DNS server: name resolution works,
so the user's "DNS not resolving" hypothesis is wrong. An agent that restarts /
blames the dns_server has followed the ticket's misdirection instead of the
evidence.

[FIX]
Restart the Apache web service on web_server_0 (e.g. `service apache2 start` /
`systemctl start apache2`). Once Apache is listening on port 80 again,
http://web0.local serves normally. The DNS server needs no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from host_1_1_1_1, curl http://web0.local (fails)
   AND nslookup web0.local against the DNS server (succeeds -> 10.200.0.3).
2. Separate name resolution from service: DNS returns the correct A record, so
   the ticket's "DNS not resolving" premise is false.
3. Test the service directly: ping 10.200.0.3 works (host up) but TCP/80 is
   closed; on web_server_0, pgrep apache2 is empty -> the web daemon is down.
4. Localize to web_server_0 (Apache), not the DNS server: the dead HTTP service
   fully explains the symptom; exonerate dns_server.

[SCORING-AXES]
assert-identifies: web_server_0
assert-not-identifies: dns_server
must-identify-web-service-down: identifies that the Apache/HTTP service on web_server_0 is stopped (TCP 80 closed), not a DNS or network fault
bonus-exonerates-dns: explicitly notes DNS still resolves web0.local correctly, rejecting the ticket's DNS hypothesis
