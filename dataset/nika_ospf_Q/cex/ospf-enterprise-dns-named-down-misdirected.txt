Scenario: ospf-enterprise-dns-named-down-misdirected
Topology: ospf_enterprise_static
Fault family: service down (misdirected ticket)
==================================================

[PROMPT-TO-AGENT]
Helpdesk ticket #8841: Users report that "web0.local" and "web1.local" will not
load at all from host_1_1_1_1 -- the portals never come up. The team has decided
that all the web servers in the server farm must have crashed and wants every
web server rebooted. Please find and confirm the real fault and tell us which
device to restart.

[INJECTION]
device: dns_server
action: stop the BIND (named) DNS service on dns_server
cmd: pkill -9 named

[POST-INJECT-CHECK]
dns_server     pgrep named               => expect empty
host_1_1_1_1   ping -W2 -c2 10.200.0.3   => expect 0% loss

[GROUND-TRUTH]
The real fault is on dns_server: its BIND (named) service is stopped, so the
campus DNS no longer resolves names -- web0.local, web1.local and the other
*.local names fail to resolve, which is why the portals never load by name. The
ticket MISDIRECTS to the web servers, but the web servers are healthy: web_server_0
(10.200.0.3) and the other web servers are UP, reachable at the IP layer (ping
succeeds), and Apache is still serving HTTP on port 80. The symptom is purely
dead name resolution, not a web-server crash and not the network.

The correct diagnosis identifies dns_server (DNS/named service down) as the
faulty device and explicitly EXONERATES the web servers: they answer HTTP when
reached by IP, so the user's "all the web servers crashed" hypothesis is wrong.
An agent that reboots / blames web_server_0 (or the other web servers) has
followed the ticket's misdirection instead of the evidence.

[FIX]
Restart the BIND DNS service on dns_server (e.g. `systemctl start named`). Once
named is resolving again, web0.local / web1.local resolve to their server IPs and
the portals load normally. The web servers need no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from host_1_1_1_1, loading web0.local / web1.local
   by name fails, but the hosts themselves are reachable by IP (ping 10.200.0.3
   succeeds).
2. Test name resolution directly: queries to the DNS server do not resolve the
   *.local names; on dns_server, pgrep named is empty -> the DNS daemon is down.
3. Separate name resolution from the web service: reaching a web server by IP
   still returns HTTP, so the ticket's "web servers crashed" premise is false.
4. Localize to dns_server (named), not the web servers: the dead DNS service fully
   explains the symptom; exonerate web_server_0 and the rest of the farm.

[SCORING-AXES]
assert-identifies: dns_server
assert-not-identifies: web_server_0
must-identify-dns-down: identifies the DNS/named service on dns_server is stopped (names do not resolve), not a web-server fault
bonus-exonerates-web-servers: notes the web servers serve HTTP when reached by IP, rejecting the "web servers crashed" hypothesis
