[GROUND-TRUTH]
This is a NEGATIVE CONTROL (false-premise) scenario. No fault was injected;
the network is at healthy baseline. The reported symptom -- Office A has lost
all Internet access -- is NOT reproducible: PC1 (10.1.0.100) reaches the ISP
edge 203.0.113.1 with 0% loss, because R1
MASQUERADEs 10.1.0.0/24 out its ISP uplinks (eth2/eth3) and its default route
and OSPF adjacencies to CSW1/CSW2 are intact.

The correct diagnosis is is_anomaly=false: the egress path is healthy and the
user's report cannot be confirmed by direct evidence. A correct agent probes
the Office A -> Internet path against the live lab (ping/curl a public
address, check R1's NAT and default route), finds it healthy, and reports no
fault. An agent that "finds" a fault here -- blaming the R1 uplink, an ISP, or
NAT to match the ticket -- is over-diagnosing: confirming the premise instead
of testing it.

Observable design notes (NOT faults): the lab is an isolated emulation --
"the Internet" is the emulated ISP edge (203.0.113.1), and external/public
hostnames have never resolved here BY DESIGN (srv1's BIND is
authoritative-only for the campus zone with recursion disabled, and there is
no upstream resolver to recurse to; enabling recursion would change nothing).
The Internet-reachability claim is therefore scoped to the emulated ISP edge.
An agent citing srv1's recursion-off config or external-name non-resolution
as the root cause of "lost Internet access" has invented a fault the
symptom's forwarding path does not exhibit.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: reproduce the claimed failure on the actual egress path
   -- from PC1 (10.1.0.100) ping/curl a public address (203.0.113.1) and

2. Check the NAT boundary on R1: `iptables -t nat -nL POSTROUTING` shows the

3. Check egress routing: R1 has a default route (via the ISP uplinks) and its

4. If all checks pass and the claimed symptom is not reproducible, conclude
   is_anomaly=false: report that the premise cannot be confirmed and the
   egress path is at healthy baseline. Do NOT invent an uplink/ISP fault to
   match the ticket.
