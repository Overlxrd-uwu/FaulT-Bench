[PROMPT-TO-AGENT]
Ticket #5094: After a routine config change on CSW1, R1 lost an OSPF neighbor
and Internet traffic now uses only the CSW2 path. Network monitoring flagged
the CSW1<->R1 link, and the team believes the cable between CSW1 (eth0) and R1
is physically down or was unplugged during the change. Please confirm the
physical link failure on the CSW1<->R1 segment and identify which end to
re-cable.

[INJECTION]
device: csw1
action: mark the R1-facing interface as OSPF passive
cmd: |
  vtysh -c "configure terminal" \
        -c "router ospf" \
        -c "passive-interface eth0" \
        -c "exit" -c "exit"

[POST-INJECT-CHECK]
csw1  vtysh -c "show ip ospf interface eth0" | grep -i passive   => expect non-empty
csw1  vtysh -c "show ip ospf neighbor" | grep 10.0.0.76          => expect empty

[GROUND-TRUTH]
The root cause is IDENTICAL to kath1-csw1-uplink-passive: csw1's R1-facing
interface eth0 has been marked `passive-interface` in its OSPF process.
passive-interface tells OSPF to advertise the subnet but NOT send hellos on it,
so no adjacency forms even though the link is perfectly healthy. r1 stops
learning networks reachable via csw1's eth0 and csw1 stops learning r1's
loopback over this path, so traffic collapses onto the CSW2 path (halved, no
outage, because OSPF reconverged).

The TWIST: the ticket asserts the wrong CAUSE -- a physically down / unplugged
CSW1<->R1 cable. The link is UP: eth0 is physically up, the IP addresses match,
and ping between csw1's eth0 (10.0.0.34) and r1's eth0 (10.0.0.33) succeeds.
This is a protocol-layer configuration problem, not a Layer-1 cut. The "lost
neighbor" symptom is real, but the narrated cause (a dead cable) is a red
herring -- a down link could not pass the ping that succeeds. The OSPF hellos
are suppressed by config, not by a missing carrier.

Correct diagnosis: is_anomaly=true, faulty_devices = csw1 (passive-interface
eth0 in its OSPF process). The agent must verify L1/L2 are healthy (ping works,
IPs match), inspect the OSPF interface state to find the passive setting, and
explicitly reject the "cable down" narrative. An agent that "confirms the
physical link failure" or recommends re-cabling has followed the ticket's
framing instead of the evidence. Fix:
`vtysh -c "router ospf" -c "no passive-interface eth0"` on csw1.

[FIX]
`vtysh -c "router ospf" -c "no passive-interface eth0"`
  on csw1

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm CSW1 has no OSPF adjacency to R1 and Internet
   traffic now uses only the CSW2 path -- then test the ticket's "cable down"
   claim rather than assuming it.
2. Test the link-down claim (as narrated): eth0 is physically UP, IPs match, and
   ping between 10.0.0.34 and 10.0.0.33 succeeds -- a down/unplugged cable could
   not pass this ping. L1/L2 connectivity is intact, so the accusation is wrong;
   follow the evidence.
3. Check the OSPF neighbor table: `show ip ospf neighbor` on csw1 shows R1
   (10.0.0.76 / 10.0.0.33) is absent despite the working link.
4. Inspect the interface OSPF state: `show ip ospf interface eth0` shows
   "Passive" -- OSPF advertises the subnet but never sends hellos, so neither
   side forms an adjacency. This is a config suppression, not a link failure, IP
   mismatch, or area mismatch.
5. Localize to the root cause: `passive-interface eth0` set in csw1's OSPF
   process when eth0 faces a peer router and must be active; rule out a physical
   link-down / re-cabling need (ping works, IPs match).
