==================================================
Scenario: kath1-ispa-ospfd-down
Topology: Kath1
Fault family: ISP OSPF advertise default down
==================================================

[PROMPT-TO-AGENT]
Internet traffic from all internal users became slower and
sometimes flaky. Active TCP connections kept working but new
connections to 203.0.113.x sometimes time out then succeed.
R1 reports it lost an OSPF neighbor. Identify which.

[INJECTION]
device: ispa
action: kill ospfd on ISPA (primary internet default-originator)
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
ispa  pgrep ospfd                                            => expect empty

[GROUND-TRUTH]
Affected component: ispa ospfd daemon
Mechanism: Both ISPA and ISPB advertise a default route into
  the OSPF domain via `default-information originate`. R1
  prefers ISPA (lower cost). When ISPA's ospfd dies, R1
  ages out the default learned from ISPA and falls back to
  ISPB's default. During the timeout + reconvergence window,
  new connections fail. Once converged on ISPB, service
  resumes but takes a slightly different path.
Localization: ispa
Root cause: ospfd not running on ispa
Fix: `/etc/init.d/frr restart` on ispa

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on ispa" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on ispa

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: Internet traffic is degraded for all internal users;
   R1 reports losing one OSPF neighbor -- identify which neighbor is gone
   (ISPA vs. ISPB).
2. Inspect R1's OSPF neighbor table: `show ip ospf neighbor` on r1 -- ISPA
   neighbor is absent; ISPB neighbor is still Full.
3. Check the routing table on R1: `ip route show default` -- the default
   route now points to ISPB's address (failover occurred) rather than ISPA.
4. Check the routing daemon on ispa: `pgrep ospfd` on ispa returns empty --
   ospfd is not running, so ISPA stopped sending OSPF hellos and its
   default-information originate advertisement was withdrawn.
5. Localize to the root cause: ospfd process not running on ispa; rule out a
   link failure (ISPA's link to R1 is up) and an OSPF configuration change
   (ISPB's adjacency is intact and uses the same configuration pattern).
