==================================================
Scenario: kath1-csw1-r1-link-down
Topology: Kath1
Fault family: core link cut
==================================================

[PROMPT-TO-AGENT]
PC users report no noticeable problems with internal traffic.
Internet access also works. But network monitoring shows R1's
ECMP path count dropped from 2 to 1 and all internet traffic
now takes a single path through CSW2 only. CSW1 reports an
OSPF neighbor went down. What changed?

[INJECTION]
device: csw1
action: shut down the link to r1
cmd: ip link set eth0 down

[POST-INJECT-CHECK]
csw1  ip -br link show eth0 | grep -c UP                    => expect 0
csw1  vtysh -c "show ip ospf neighbor" | grep 10.0.0.76     => expect empty
r1    vtysh -c "show ip route" | grep -c "via 10.0.0.33"    => expect 0

[GROUND-TRUTH]
Affected component: csw1 eth0 / link CSW1 <-> R1 (10.0.0.32/30)
Mechanism: r1 has two ECMP-eligible paths to the OSPF backbone
  via CSW1 (10.0.0.33) and CSW2 (10.0.0.37). With CSW1's eth0
  down, the adjacency drops and the CSW1-side path is removed.
  All traffic falls onto the CSW2 path; capacity is halved
  but no outage because OSPF converges.
Localization: csw1 (eth0)
Root cause: physical/logical link between CSW1 and R1 is down
Fix: `ip link set eth0 up` on csw1 (or investigate cabling if
  in real hardware)

[FIX]
`ip link set eth0 up` on csw1 (or investigate cabling if
  in real hardware)

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm csw1's OSPF neighbor went down and r1's ECMP
   path count dropped 2 -> 1; verify the report rather than assuming it.
2. Layer 1/2 first: check interface/link state on csw1 -> eth0 is down.
3. Layer 3 control plane: confirm the OSPF adjacency to 10.0.0.76 dropped as
   a CONSEQUENCE of the link, not from an OSPF configuration change.
4. Correlate: lost adjacency -> CSW1 nexthop withdrawn -> traffic collapses
   onto the CSW2 path; capacity halved but no outage (OSPF reconverged).
5. Localize to the lowest layer: physical/logical link CSW1<->R1
   (10.0.0.32/30), not a protocol misconfiguration or cost change.
