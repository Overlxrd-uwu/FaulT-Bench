Topology: Kath1
Fault family: VRRP daemon down (master)

[PROMPT-TO-AGENT]
Office A users report a brief connectivity outage to their
default gateway (10.1.0.1, 10.6.0.1, 10.0.0.1), then service
restored. After the event, traffic appears to take a slightly
longer path. The gateways still respond. Find what caused the
event.

[INJECTION]
device: dswa1
action: stop keepalived (kills all VRRP instances on the MASTER)
cmd: pkill -9 keepalived

[POST-INJECT-CHECK]
dswa1  pgrep keepalived                        => expect empty
pc1    ping -W2 -c2 10.1.0.1                   => expect 0% loss (BACKUP took over)
dswa2  ip -br addr show br0.10 | grep 10.1.0.1   => expect non-empty

[GROUND-TRUTH]
Affected component: dswa1 keepalived process (VRRP daemon)
Mechanism: dswa1 was VRRP MASTER for VIs 10, 20, 40, 99 on
  Office A side (priorities 105 / 1 / 1 / 105). Killing
  keepalived stops VRRP advertisements; after the dead
  interval (~3s) dswa2 takes over MASTER for all of them.
  Briefly during failover, packets to VIPs are dropped.
  Steady state restores once dswa2 owns the VIPs.
Localization: dswa1
Root cause: keepalived not running on dswa1
Fix: `/etc/init.d/keepalived start` on dswa1

[FIX]
`/etc/init.d/keepalived start` on dswa1

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: brief outage affecting all Office A VIP gateways
   (10.1.0.1, 10.6.0.1, 10.0.0.1) then recovery -- all VIPs went dark
   simultaneously, pointing to a shared mechanism rather than a per-VLAN
   SVI fault.
2. Check VRRP/VIP state after the event: `ip -br addr show br0.10` on dswa2
   now holds 10.1.0.1 -- dswa2 is the new MASTER; dswa1 no longer holds
   any VIPs.
3. Check keepalived process on dswa1: `pgrep keepalived` returns empty --
   the VRRP daemon is not running, so dswa1 stopped all VRRP advertisements.
4. Trace the mechanism: with no VRRP advertisements from dswa1, dswa2 waits
   out the dead interval (~3s) then takes MASTER for VIs 10, 20, 40, 99;
   during that window packets to VIPs are dropped, causing the observed
   brief outage.
5. Localize to the root cause: keepalived daemon not running on dswa1; rule
   out a per-SVI failure (all VLANs affected together) and a network link
   issue (dswa1 is otherwise reachable).
