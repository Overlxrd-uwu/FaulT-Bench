==================================================
Scenario: simple-bgp-pc2-no-default-route
Topology: simple_bgp
Fault family: host misconfig (missing default route)
==================================================

[PROMPT-TO-AGENT]
The user on pc2 (200.1.1.2) reports every attempt to reach the
partner network fails instantly with "Network is unreachable" --
no timeout, an immediate error. pc2 still reaches its own gateway
200.1.1.1 fine. The partner side reports pings from pc1 to pc2
time out. It started right after maintenance on pc2. Diagnose.

[INJECTION]
device: pc2
action: delete pc2's default route (host left with only its connected subnet)
cmd: ip route del default

[POST-INJECT-CHECK]
pc2   ip route show default | grep -c via                   => expect 0
pc2   ping -c 2 -W 2 195.11.14.1 >/dev/null 2>&1; echo $?   => expect 2
pc1   ping -W2 -c2 200.1.1.2                                => expect loss>0

[GROUND-TRUTH]
Affected component: pc2 default route / gateway configuration
Mechanism: pc2's default route (via 200.1.1.1) has been deleted,
  leaving only the connected 200.1.1.0/24 route. Any packet to an
  off-subnet destination fails immediately in pc2's own kernel
  with ENETUNREACH ("Network is unreachable") -- nothing is even
  transmitted, which is why the error is instant rather than a
  timeout. On-subnet traffic to 200.1.1.1 still works. The network
  side is fully healthy: router2 still advertises 200.1.1.0/24,
  the eBGP session is Established, and pc1's pings ARE delivered
  to pc2 -- but pc2 has no route for the replies, so pc1 sees
  timeouts.
Localization: pc2
Root cause: missing default route on pc2 (no gateway configured)
Fix: `ip route add default via 200.1.1.1 dev eth0` on pc2

[FIX]
Restore pc2's default route -- `ip route add default via 200.1.1.1 dev eth0`
on pc2. Off-subnet connectivity returns immediately; no router or BGP change
is needed.

[DIAGNOSTIC-PROCESS]
1. Scope to pc2: the instant "Network is unreachable" error is generated by
   pc2's own kernel (a routing-table miss), unlike a silent in-network drop
   which would time out. On-subnet pings to 200.1.1.1 still work.
2. Inspect pc2's routing table: `ip route` shows only the connected
   200.1.1.0/24 entry -- the default route is gone.
3. Verify the network is not the problem: router2 advertises 200.1.1.0/24, the
   eBGP session is Established, and inbound packets reach pc2; only pc2's
   replies have no route.
4. Localize to pc2's missing default route: a host-side misconfiguration, not
   a router, link or BGP fault.

[SCORING-AXES]
assert-identifies: pc2
must-identify-device: pc2 (host-side issue)
must-identify-component: missing default route (no gateway configured)
must-explain-instant-error: ties the instant "Network is unreachable" to a local routing-table miss on pc2, not a network-side failure
bonus-exonerates-network: notes the eBGP session, the prefix advertisements and delivery to pc2 are all healthy; only pc2's replies are unroutable
