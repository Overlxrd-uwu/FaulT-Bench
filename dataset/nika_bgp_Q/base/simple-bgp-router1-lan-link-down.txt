==================================================
Scenario: simple-bgp-router1-lan-link-down
Topology: simple_bgp
Fault family: link cut (LAN leg)
==================================================

[PROMPT-TO-AGENT]
The user on pc1 (195.11.14.2) reports total network loss: they
cannot reach pc2 (200.1.1.2), and they cannot even ping their own
gateway 195.11.14.1. pc1's own NIC still shows link up. The
partner AS is healthy internally: pc2 reaches its gateway
200.1.1.1 fine. Find what broke.

[INJECTION]
device: router1
action: administratively down the LAN interface (eth1) toward pc1 on router1
cmd: ip link set eth1 down

[POST-INJECT-CHECK]
router1   ip -br link show eth1 | grep -c UP  => expect 0
pc1       ping -W2 -c2 195.11.14.1           => expect loss>0

[GROUND-TRUTH]
Affected component: router1 eth1 (195.11.14.1/24, the LAN
  interface toward pc1)
Mechanism: router1's eth1 is DOWN, so pc1's only gateway address
  195.11.14.1 is gone from the segment -- pc1 cannot even ARP its
  gateway and loses all off-host connectivity. On router1 the
  connected route 195.11.14.0/24 disappears from the RIB, so the
  `network 195.11.14.0/24` statement has no matching route and
  the prefix is withdrawn from BGP -- AS 2 also loses its path to
  pc1. pc1's own NIC still shows link up (its side of the virtual
  segment is unaffected), which is why a host-side check looks
  clean. The inter-AS link and the eBGP session machinery are not
  the fault; the failure sits on the router1<->pc1 LAN leg.
Localization: router1
Root cause: router1 eth1 (LAN link to pc1) is down
Fix: `ip link set eth1 up` on router1

[FIX]
`ip link set eth1 up` on router1. The gateway 195.11.14.1 comes back on the
segment, the connected route returns and BGP re-advertises 195.11.14.0/24
automatically; pc1 reaches pc2 normally. pc1 needs no change.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: pc1 cannot reach even its own gateway 195.11.14.1, while
   AS 2 is internally healthy -- the fault is on the pc1<->router1 LAN leg, not
   the inter-AS path.
2. Check pc1's side: its IP (195.11.14.2/24), default route and link state are
   all correct -- the host is not the problem.
3. Check the other end of the segment: on router1, `ip -br link show eth1`
   shows the interface DOWN.
4. Correlate with routing: with eth1 down the connected 195.11.14.0/24 route is
   gone and the prefix is withdrawn from BGP, so AS 2 has no path to pc1 either.
5. Localize to router1 eth1 down: rule out a bgpd crash (daemon runs, session
   machinery fine) and the inter-AS link (eth0 is UP).

[SCORING-AXES]
assert-identifies: router1
must-identify-device: router1
must-identify-component: eth1 (the 195.11.14.0/24 LAN interface toward pc1) is down
must-distinguish-symptom-pattern: pc1 cannot even reach its gateway, so the fault is on the pc1<->router1 LAN leg, not the inter-AS link or the BGP session
bonus-rules-out-host: notes pc1's own link/IP/route are intact; the failure is on router1's side of the segment
