==================================================
Scenario: simple-bgp-interas-link-down-misdescribed
Topology: simple_bgp
Fault family: link down (misdescribed ticket)
==================================================

[PROMPT-TO-AGENT]
Helpdesk ticket #9103: A user on pc1 (195.11.14.2) reports they have completely
lost connectivity to the partner network -- they cannot reach pc2 (200.1.1.2) in
the peer AS since this morning. The team is convinced someone fat-fingered the
BGP configuration overnight and want the BGP config rolled back. Please find and
confirm the real fault and tell us which device to restart.

[INJECTION]
device: router1
action: administratively down the inter-AS interface (eth0) on router1
cmd: ip link set eth0 down

[POST-INJECT-CHECK]
router1   ip -br link show eth0 | grep -c UP => expect 0
pc1       ping -W2 -c2 200.1.1.2             => expect loss>0

[GROUND-TRUTH]
The real fault is the inter-AS link: router1's eth0 (the interface to router2)
is DOWN, so the physical/L2 path between the two ASes is broken. As a CONSEQUENCE
the eBGP session between router1 and router2 drops and the inter-AS prefixes are
withdrawn, so pc1 (195.11.14.2) cannot reach pc2 (200.1.1.2). The ticket
MISDESCRIBES the cause as a BGP configuration error, but the BGP configuration is
intact and unchanged -- the session is down purely because the underlying link is
down, not because of any config mistake.

The correct diagnosis identifies router1 (inter-AS link / eth0 down) as the root
cause and explicitly notes the BGP loss is a downstream EFFECT, not the cause: the
BGP configuration on router1 and router2 is unchanged, so the user's "someone
broke the BGP config" hypothesis is wrong. An agent that rolls back / blames the
BGP configuration has accepted the ticket's misdescription instead of testing it.

[FIX]
Bring the inter-AS link back up: on router1 run `ip link set eth0 up`. Once eth0
is up again, the eBGP session to router2 re-establishes, the inter-AS prefixes are
re-exchanged, and pc1 reaches pc2 normally. The BGP configuration needs no change
-- it was never modified.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from pc1, ping pc2 (200.1.1.2) -- it fails (no
   route to the peer AS).
2. Check the data/physical layer: on router1 the inter-AS interface eth0 is DOWN
   (no carrier) -> the link itself is broken.
3. Check the control plane and config: the eBGP session is down BECAUSE the link
   is down; the BGP configuration on router1/router2 is intact and unchanged, so
   the ticket's "misconfigured BGP" premise is false.
4. Localize to the inter-AS link (router1 eth0 down) as the root cause, with the
   BGP session loss as a consequence -- not a config error.

[SCORING-AXES]
assert-identifies: router1
must-identify-link-down: identifies the inter-AS link (router1 eth0) is down as the root cause, with BGP loss as a consequence
bonus-rules-out-bgp-config: notes the BGP configuration is intact/unchanged, rejecting the "misconfigured BGP" cause
