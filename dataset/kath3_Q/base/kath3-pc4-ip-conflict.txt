==================================================
Scenario: kath3-pc4-ip-conflict
Topology: Kath3
Fault family: IP address conflict
==================================================

[PROMPT-TO-AGENT]
PC4 (172.16.10.4) and PC5 (was 172.16.10.5) in Location A
both intermittently lose connectivity. ARP for 172.16.10.4
flips between two MAC addresses on the switch. Internal pings
between PC4 and the gateway sometimes succeed, sometimes fail.
Diagnose.

[INJECTION]
device: pc5
action: reconfigure pc5 to PC4's IP (172.16.10.4 — collision)
cmd: |
  ip addr flush dev eth0
  ip addr add 172.16.10.4/24 dev eth0
  ip route add default via 172.16.10.1 2>/dev/null

[POST-INJECT-CHECK]
pc5      ip -4 -br addr show eth0 | grep -c "172.16.10.4"  => expect 1

[GROUND-TRUTH]
Affected component: pc5 IP configuration — duplicate of pc4
Mechanism: Both PC4 and PC5 advertise themselves as
  172.16.10.4 via ARP. The switch FDB and the gateway's ARP
  cache flip between their MACs as they respond to each other's
  gratuitous ARPs. Return traffic destined for .4 randomly goes
  to either host, causing flaky connectivity for both.
Localization: pc5 (and pc4 secondarily, since the IP collision
  is symmetric)
Root cause: pc5 was misconfigured with 172.16.10.4 (duplicate of pc4)
Fix: restore pc5 to its original IP (172.16.10.5)

[FIX]
restore pc5 to its original IP (172.16.10.5)

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm the connectivity is intermittent/flapping rather than a
   hard failure -- both PC4 and the affected path show inconsistent ping results.
2. Look for ARP anomalies: inspect the switch FDB or ARP cache and observe that
   172.16.10.4 flips between two different MAC addresses -- signature of an IP conflict.
3. Identify both claimants: determine which two devices are asserting 172.16.10.4 (PC4
   and PC5) by correlating MACs to interface hardware addresses on each host.
4. Confirm the misconfigured host: check `ip addr show` on PC5 and confirm it was
   reconfigured with 172.16.10.4 instead of its original 172.16.10.5.
5. Localize to the lowest-layer root cause: PC5 has a duplicate IP (host-side
   misconfiguration); rule out a VLAN, switch, or routing fault since all other hosts
   on the segment behave normally.
