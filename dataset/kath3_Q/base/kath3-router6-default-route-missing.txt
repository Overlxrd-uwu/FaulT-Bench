==================================================
Scenario: kath3-router6-default-route-missing
Topology: Kath3
Fault family: default route missing (asymmetric impact)
==================================================

[PROMPT-TO-AGENT]
After a config change on router6, traffic destined to subnets that
are not in router6's RIP-learned table fails. Local intra-Location-B
traffic still works, and RIP-learned destinations (172.16.10.0/24,
192.168.100.0/24, etc.) are reachable. But router6 itself can no
longer reach any external/unknown destination. Diagnose what was
removed on router6.

[INJECTION]
device: router6
action: remove the default route (router6 originally has
  `ip route 0.0.0.0 0.0.0.0 10.50.1.1 150`)
cmd: ip route del default

[POST-INJECT-CHECK]
router6  ip route show default                  => expect empty
# router6 still has RIP-learned routes, but anything not in its RIB now
# has no fallback. Use a destination outside its RIP scope to confirm.
router6  ping -W2 -c2 8.8.8.8                   => expect loss>0

[GROUND-TRUTH]
Affected component: router6 default route
Mechanism: router6 has RIP-learned routes for the topology's
  internal prefixes, but anything outside that scope (e.g.
  8.8.8.8, external WAN destinations) relied on the static
  default route via 10.50.1.1. Without it, router6 drops any
  packet whose destination is not in its RIB.
  Intra-Location-B traffic is unaffected because router6 has
  directly-connected / RIP-learned routes for those prefixes.
  (Note: Location B -> Location A is independently blocked by
  router6's WAN-side ACL 110, so do NOT use cross-Location
  pings as a test signal here.)
Localization: router6
Root cause: default route missing on router6
Fix: `ip route add default via 10.50.1.1 metric 150` on router6

[FIX]
`ip route add default via 10.50.1.1 metric 150` on router6

[DIAGNOSTIC-PROCESS]
1. Scope the failing traffic class: confirm that RIP-learned destinations
   (172.16.10.0/24, 192.168.100.0/24, etc.) are still reachable from router6 while
   destinations outside the RIP-learned table are not -- the failure is selective by
   prefix, not a complete outage.
2. Inspect router6's routing table: run `ip route show` on router6 -- RIP-learned
   routes are present but there is no default route entry.
3. Confirm the default route is missing: verify `ip route show default` returns
   empty; the original static default via 10.50.1.1 was removed.
4. Confirm next-hop reachability: verify 10.50.1.1 is still pingable from router6
   (the upstream path is intact; only the route entry is gone), ruling out an upstream
   link failure.
5. Localize to the lowest-layer root cause: router6 is missing its static default
   route (0.0.0.0/0 via 10.50.1.1); rule out a RIP misconfiguration or interface
   failure. Note: do NOT use Location B -> Location A cross-location pings to diagnose
   this fault; that path is blocked by router6's ACL 110 by design.
