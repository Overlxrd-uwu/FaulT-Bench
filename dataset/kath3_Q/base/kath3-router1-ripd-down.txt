==================================================
Scenario: kath3-router1-ripd-down
Topology: Kath3
Fault family: routing daemon down (core transit)
==================================================

[PROMPT-TO-AGENT]
Multiple zones report partial loss of reachability to each other after a change
on router1, a core transit router. Hosts within each zone still reach their own
gateways. router1's interfaces appear up. Diagnose what stopped on router1.

[INJECTION]
device: router1
action: kill ripd (kill watchfrr first so FRR does not respawn it)
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router1  pgrep ripd                                       => expect empty
router1  ip -br link show | grep -c -w UP                 => expect >=1

[GROUND-TRUTH]
Affected component: router1 ripd
Mechanism: router1 is a core transit router in the RIP domain. With ripd dead it
  stops advertising and relearning RIP routes, so prefixes that transit router1
  age out across the network and the zones it bridges lose reachability to each
  other. Intra-zone traffic and router1's own interfaces are unaffected, which is
  the tell that the fault is the routing daemon, not a link.
Localization: router1
Root cause: ripd not running on router1
Fix: restart FRR AND re-apply the `router rip` configuration on router1 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router1" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on router1

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router1. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm inter-zone reachability degraded while intra-zone
   traffic and gateways still work -- a control-plane fault on a transit router,
   not a host or link issue.
2. Inspect routing tables: check that RIP routes which transit router1 have aged
   out on neighboring routers, indicating router1 stopped advertising/relearning.
3. Check RIP adjacency/updates: router1 is no longer exchanging RIP updates with
   its neighbors.
4. Check the daemon on router1: `pgrep ripd` is empty -- ripd is not running.
5. Localize to the daemon: the fault is ripd dead on router1; rule out a link
   failure by confirming router1's interfaces are up and a host issue by noting
   intra-zone traffic is fine.
