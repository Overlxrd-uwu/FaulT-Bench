==================================================
Scenario: kath3-router0-ripd-down-misdirected
Topology: Kath3
Fault family: routing daemon down (misdirected prompt)
==================================================

[PROMPT-TO-AGENT]
Location A users (PC4/PC5 on VLAN 10, Laptop0 on VLAN 20) opened ticket #7012:
they cannot reach Location C or anything outside Location A, although hosts
inside Location A still reach each other and their gateways. The team has been
watching mswitch1 (the Location A access switch that trunks VLAN 10/20) and is
convinced its uplink trunk is dropping the inter-VLAN / uplink traffic. Please
confirm the mswitch1 trunk fault and identify the affected port.

[INJECTION]
device: router0
action: kill ripd (kill watchfrr first so FRR does not respawn it)
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router0  pgrep ripd                                       => expect empty
pc4      ping -W2 -c2 192.168.100.1                        => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath3-router0-ripd-down: ripd is dead on router0.
router0 is Location A's only L3 egress; with ripd stopped it no longer advertises
172.16.10.0/24 and 172.16.20.0/24 upstream and no longer learns the rest of the
network's RIB, so Location A becomes a routing island. Internal Location A traffic
(and the VLAN 10/20 gateways on router0's sub-interfaces) still works -- exactly
the reported pattern.

The TWIST: the ticket blames mswitch1. mswitch1 is HEALTHY -- it is a pure L2
switch that bridges VLAN 10/20 between the hosts and router0; it carries no RIP
state and its trunks are forwarding. This is first-hop / symptom-site bias: the
team blames the device nearest the users. A decisive tell: if the mswitch1 trunk
were down, hosts would also lose their own gateway (172.16.10.1 / 172.16.20.1)
and their intra-VLAN peers -- but those still work, so L2 is intact and the fault
is upstream at router0's routing.

Correct diagnosis: is_anomaly=true, faulty_devices = router0 (ripd not running).
The agent must localise from evidence -- router0's dead ripd and Location A
prefixes aged out on router1 -- and explicitly NOT pin the fault on mswitch1. An
agent that "confirms the mswitch1 trunk fault" has followed the accusation
instead of the evidence. Fix: restart FRR AND re-apply the `router rip` configuration on router0 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router0" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
Restart FRR / the ripd daemon on router0 (e.g. `/etc/init.d/frr restart` on
router0). Once ripd is running again it re-advertises and re-learns the
affected routes, restoring reachability. (The ticket misattributes the fault;
the remediation targets router0.)

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router0. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm Location A loses everything outside while intra-VLAN
   and gateways work -- an L3 egress/routing fault -- before accepting the
   mswitch1 trunk hypothesis.
2. Check mswitch1 first (as accused): it is an L2 switch; hosts still reach their
   gateways (172.16.10.1 / 172.16.20.1) and intra-VLAN peers through it, so its
   trunks are forwarding. A trunk fault would also break those -- it did not.
3. Follow the evidence upstream: from router1, Location A's prefixes
   (172.16.10.0/24, 172.16.20.0/24) have aged out of RIP -- router0 stopped
   advertising.
4. Inspect router0: `pgrep ripd` is empty -- ripd is dead, so router0 no longer
   exchanges RIP and Location A is islanded.
5. Localize to the root cause: ripd not running on router0; mswitch1 is a healthy
   L2 bystander, not the cause.
