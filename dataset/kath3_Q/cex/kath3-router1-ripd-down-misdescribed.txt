==================================================
Scenario: kath3-router1-ripd-down-misdescribed
Topology: Kath3
Fault family: routing daemon down (misdescribed cause)
==================================================

[PROMPT-TO-AGENT]
Ticket #7055: After a change on router1 (a core transit router), multiple zones
report partial loss of reachability to each other, though hosts within each zone
still reach their own gateways. The team believes the router0<->router1 link is
physically down -- "the cable/serial between router0 and router1 dropped during the
change." Please confirm the router0<->router1 link failure and identify the down
interface.

[INJECTION]
device: router1
action: kill ripd (kill watchfrr first so FRR does not respawn it)
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router1  pgrep ripd                                       => expect empty
router1  ip -br link show | grep -c -w UP                 => expect >=1

[GROUND-TRUTH]
The root cause is IDENTICAL to kath3-router1-ripd-down: ripd is dead on router1.
router1 is a core transit router in the RIP domain; with ripd stopped it no longer
advertises or relearns RIP routes, so prefixes that transit router1 age out across
the network and the zones it bridges lose reachability to each other. Intra-zone
traffic and router1's own interfaces are unaffected.

The TWIST: the ticket asserts the wrong CAUSE -- a physically down router0<->router1
link. The link is actually UP: router1's interfaces are up and forwarding (the
post-inject check confirms router1 still has UP links), and nothing physical failed.
The "inter-zone reachability loss" symptom is real, but the narrated cause (a
dropped cable/serial) is a red herring -- the routing daemon silently died, the wire
did not. A live link with a dead routing daemon produces exactly this symptom.

Correct diagnosis: is_anomaly=true, faulty_devices = router1 (ripd not running). The
agent must check Layer 1/2 (router1's interfaces, including the router0<->router1
link, are UP), then the routing daemon (ripd dead), and explicitly reject the "link
down" narrative. An agent that "confirms the down router0<->router1 link" has
followed the ticket's framing instead of the evidence. Fix: restart FRR AND re-apply the `router rip` configuration on router1 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router1" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on router1

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router1. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm inter-zone reachability degraded while intra-zone
   traffic and gateways still work -- then TEST the ticket's "link down" claim
   rather than assuming it.
2. Layer 1/2 first: check router1's interfaces, including the link toward router0 --
   they are UP and forwarding. The narrated physical link failure did not happen.
3. Check the routing protocol: `pgrep ripd` on router1 is empty -- ripd is dead. A
   live link with a dead routing daemon produces exactly this inter-zone symptom.
4. Confirm propagation: RIP routes that transit router1 have aged out on neighboring
   routers because router1 stopped advertising/relearning.
5. Localize to the root cause: ripd not running on router1 -- NOT a link failure.
   router1's links (including router0<->router1) are up; the routing daemon is the
   fault.
