[PROMPT-TO-AGENT]
PC11-14 in Location C (192.168.200.x) opened ticket #7048: they cannot reach
Location A (172.16.10.x, 172.16.20.x) at all, while other zones still reach each
other. The team is convinced router3 is the culprit -- "router3 dropped the link
toward Location C; please confirm router3 has failed and replace router3." Confirm
the router3 fault and identify what to swap out.

[INJECTION]
device: router4
action: shut down BOTH of router4's upstream links -- Location C is dual-homed (eth5 -> router3 over 172.25.1.x AND eth4 -> router5 over 192.168.15.x); both must drop to isolate it
cmd: |
  ip link set eth5 down
  ip link set eth4 down

[POST-INJECT-CHECK]
router4   ip -br link show eth5 | grep -c UP      => expect 0
router4   ip -br link show eth4 | grep -c UP      => expect 0
pc11      ping -W2 -c2 172.16.10.4                => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath3-router4-r3-link-down: both of router4's
upstream links are down. router4 (Location C's edge) is DUAL-HOMED to the rest of
the network -- via router3 over 172.25.1.0/24 (eth5) AND via router5 over
192.168.15.0/24 (eth4). Both uplinks are down on router4's side, so RIP withdraws
every path and Location C is isolated from Locations A and B.

The TWIST: the ticket blames router3 and demands router3 be replaced. router3 is
HEALTHY -- its side of the 172.25.1.0/24 link is up, and it still carries transit
for the other zones (Locations A and B remain mutually reachable through it).
Replacing router3 would fix nothing. This is symptom-site / peer bias: the team
blames the neighbor across the link instead of checking which end is actually down.
A decisive tell: if router3 had failed, the other zones it transits would also
degrade -- they did not; only Location C, hanging off router4, is isolated, and the
down interfaces are on router4 (eth5 and eth4), not on router3.

Correct diagnosis: is_anomaly=true, faulty_devices = router4 (both uplinks eth5 ->
router3 and eth4 -> router5 down). The agent must localise from evidence --
router4's two down uplinks versus router3's up interfaces and intact transit -- and
explicitly NOT pin the fault on router3. An agent that "confirms the router3 fault"
or recommends replacing router3 has followed the accusation instead of the
evidence. Fix: `ip link set eth5 up; ip link set eth4 up` on router4.

[FIX]
`ip link set eth5 up; ip link set eth4 up` on router4

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm Location C (PC11-14, 192.168.200.x) cannot reach
   Locations A or B while A and B still reach each other -- the fault isolates
   Location C -- before accepting the router3 hypothesis.
2. Check router3 first (as accused): router3's interfaces are up and it still
   carries transit for Locations A and B (they remain mutually reachable through
   it). A failed router3 would break those too -- it did not, so router3 is not the
   cause and need not be replaced.
3. Identify Location C's WAN egress: router4 is Location C's edge, dual-homed via
   router3 over 172.25.1.0/24 (eth5) and via router5 over 192.168.15.0/24 (eth4).
4. Check link state on router4: `ip -br link show eth5` and `eth4` on router4 are
   both down. Because Location C is dual-homed, both had to drop to isolate it --
   and both are down on router4's side.
5. Confirm the RIP consequence: Location C's prefix (192.168.200.0/24) has been
   withdrawn from the RIP table, consistent with router4's uplinks going down.
6. Localize to the root cause: both of router4's upstream links (eth5 -> router3
   and eth4 -> router5) are down; router3 is a healthy peer whose side is up, not
   the cause.
