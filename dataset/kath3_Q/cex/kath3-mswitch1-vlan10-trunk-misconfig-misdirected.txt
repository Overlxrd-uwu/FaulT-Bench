[PROMPT-TO-AGENT]
PC4 and PC5 (Location A VLAN 10, 172.16.10.0/24) opened ticket #7041: they can no
longer reach their gateway (172.16.10.1) or anything off their VLAN. Laptop0 on
VLAN 20 in the same Location is unaffected. The team has been staring at router0
and is convinced its VLAN-10 sub-interface failed during the last change --
"router0's VLAN-10 sub-interface (eth0.10) went down and stopped serving VLAN 10."
Please confirm the router0 VLAN-10 sub-interface fault and identify the down
interface.

[INJECTION]
device: mswitch1
action: bring down the VLAN 10 trunk subinterface on the
  uplink toward router0
cmd: ip link set eth0.10 down

[POST-INJECT-CHECK]
mswitch1  ip -br link show eth0.10 | grep -c UP  => expect 0
pc4       ping -W2 -c2 172.16.10.1               => expect loss>0
laptop0   ping -W2 -c2 172.16.20.1               => expect 0% loss

[GROUND-TRUTH]
The root cause is IDENTICAL to kath3-mswitch1-vlan10-trunk-misconfig: mswitch1's
VLAN 10 trunk subinterface (eth0.10) toward router0 is administratively down. With
eth0.10 down on mswitch1, no VLAN 10 frames cross the uplink, so PC4/PC5 cannot ARP
or reach their gateway (172.16.10.1). VLAN 20 rides eth0.20, which is up -- exactly
why Laptop0 is unaffected.

The TWIST: the ticket blames router0's VLAN-10 sub-interface. router0 is HEALTHY --
its eth0.10 (172.16.10.1) is up and configured; the gateway itself never failed.
This is first-hop / symptom-site bias aimed at the L3 device: the team assumes the
gateway must be down because the gateway is unreachable. A decisive tell: the break
is VLAN-scoped (VLAN 10 dead, VLAN 20 fine) and lives on the L2 trunk between the
hosts and router0. If router0's eth0.10 were the problem you would still see VLAN 10
frames reach router0 (and fail there); instead the frames never leave mswitch1
because its eth0.10 trunk subif is down.

Correct diagnosis: is_anomaly=true, faulty_devices = mswitch1 (eth0.10 trunk subif
down). The agent must localise from evidence -- mswitch1's down eth0.10 versus
router0's healthy eth0.10 -- and explicitly NOT pin the fault on router0. An agent
that "confirms the router0 VLAN-10 sub-interface fault" has followed the accusation
instead of the evidence. Fix: `ip link set eth0.10 up` on mswitch1.

[FIX]
`ip link set eth0.10 up` on mswitch1

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm only PC4/PC5 (VLAN 10) are affected while Laptop0
   (VLAN 20) still reaches its gateway -- the fault is VLAN-scoped, not a full
   outage -- before accepting the router0 sub-interface hypothesis.
2. Check router0 first (as accused): inspect router0's eth0.10 (172.16.10.1) -- it
   is up and configured; the gateway sub-interface did not fail. A router0 eth0.10
   fault is not what the evidence shows.
3. Check the L2 trunk toward router0: inspect the per-VLAN subinterfaces on
   mswitch1's uplink -- eth0.10 (VLAN 10) is down while eth0.20 (VLAN 20) is up,
   which precisely matches the VLAN-scoped symptom.
4. Confirm VLAN scope: VLAN 20 frames still cross eth0.20 and Laptop0 reaches
   172.16.20.1 -- the uplink hardware and router0 are fine; only the VLAN 10 trunk
   subif is down.
5. Localize to the root cause: mswitch1 eth0.10 trunk subinterface administratively
   down; router0 is a healthy bystander, not the cause.
