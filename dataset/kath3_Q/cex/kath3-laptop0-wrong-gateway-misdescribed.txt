[PROMPT-TO-AGENT]
Ticket #7062: Laptop0 (172.16.20.10, Location A VLAN 20) cannot reach anything
outside its own VLAN -- not Location C, not the rest of the network -- though it
still reaches other VLAN 20 hosts. PC4/PC5 on VLAN 10 are unaffected. The team
believes the gateway router is at fault -- "router0's VLAN-20 sub-interface (the
gateway, 172.16.20.1) went down, so VLAN 20 lost its gateway." Please confirm the
router0 VLAN-20 sub-interface fault and identify the down interface.

[INJECTION]
device: laptop0
action: point Laptop0's default route at a non-existent in-subnet gateway
cmd: |
  ip route del default 2>/dev/null
  ip route add default via 172.16.20.99

[POST-INJECT-CHECK]
laptop0  ip route show default | grep -c "172.16.20.99"   => expect 1
laptop0  ping -W2 -c2 192.168.100.1                        => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath3-laptop0-wrong-gateway: Laptop0's own default
gateway is misconfigured. Laptop0's correct gateway is 172.16.20.1 (router0's VLAN
20 sub-interface) but it was set to 172.16.20.99 -- in-subnet but unassigned -- so
ARP for the gateway never resolves and Laptop0 cannot forward off-subnet traffic.
VLAN 20 peers stay reachable via direct ARP.

The TWIST: the ticket asserts the wrong CAUSE -- a downed router0 VLAN-20
sub-interface. The gateway/router is actually fine: router0's eth0.20 (172.16.20.1)
is up and serving VLAN 20. The tell that this is host-scoped, not router-scoped, is
that ONLY Laptop0 is affected -- if router0's VLAN-20 sub-interface were down, every
VLAN 20 host (and their inter-VLAN traffic) would lose the gateway, not just
Laptop0. The narrated router fault is a red herring; the fault lives in Laptop0's own
L3 config.

Correct diagnosis: is_anomaly=true, faulty_devices = laptop0 (default gateway
misconfigured to 172.16.20.99). The agent must inspect Laptop0's host routing (the
default points at the wrong, unassigned gateway), confirm router0's real gateway
172.16.20.1 is up, and explicitly reject the "router sub-interface down" narrative.
An agent that "confirms the router0 VLAN-20 sub-interface fault" has followed the
ticket's framing instead of the evidence. Fix: restore Laptop0's default route --
`ip route add default via 172.16.20.1`.

[FIX]
restore Laptop0's default route -- `ip route add default via 172.16.20.1`

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm ONLY Laptop0 cannot reach off-VLAN destinations while
   its VLAN 20 peers are reachable and other VLAN 20 hosts are fine -- then TEST the
   ticket's "router sub-interface down" claim rather than assuming it.
2. Rule out the router-side cause first (as accused): router0's eth0.20
   (172.16.20.1) is up and serving VLAN 20. A down VLAN-20 sub-interface would break
   every VLAN 20 host, not just Laptop0 -- so the narrated router fault did not
   happen.
3. Inspect Laptop0's routing: `ip route show default` -- the default points at
   172.16.20.99 rather than the expected 172.16.20.1.
4. Confirm the ARP consequence: 172.16.20.99 is in-subnet but unassigned, so the
   gateway never resolves and no off-subnet packet egresses.
5. Localize to the root cause: Laptop0's host config -- its default gateway set to
   172.16.20.99 instead of 172.16.20.1. NOT a router0 sub-interface failure; the
   real gateway is up.
