[PROMPT-TO-AGENT]
Helpdesk ticket #9106: A user on pc_0_0 (10.0.0.2) reports they lost all
connectivity -- pc_0_0 can't reach pc_0_1 (10.0.1.2) or anything across the
fabric. The team is convinced it is the host -- they say "pc_0_0's host NIC or
its cabling is faulty" and want the workstation's network card and cable swapped.
Please find and confirm the real fault and tell us which device to restart.

[INJECTION]
device: leaf_router_0_0
action: take down pc_0_0's access link (eth2) on leaf_router_0_0
cmd: ip link set eth2 down

[POST-INJECT-CHECK]
leaf_router_0_0   ip -br link show eth2 | grep -c UP  => expect 0
pc_0_0            ping -W2 -c2 10.0.1.2               => expect loss>0

[GROUND-TRUTH]
The real fault is on leaf_router_0_0: pc_0_0's access link -- the host-facing
interface eth2 (leaf_router_0_0 -> pc_0_0) -- is DOWN, so pc_0_0 (10.0.0.2) is
cut off at its own top-of-rack leaf and cannot reach pc_0_1 (10.0.1.2) or anything
beyond. The ticket MISDESCRIBES the fault as a host-side problem, but pc_0_0
itself is fine: the down interface is the LEAF's access port (leaf_router_0_0
eth2), not the host's NIC or cable. Swapping pc_0_0's network card / cabling would
not bring the leaf's administratively/operationally down access port back up.

The correct diagnosis identifies leaf_router_0_0 (host-facing access link eth2
down) as the faulty device and explicitly REJECTS the host-NIC/cable cause: the
fault is on the leaf's access port, so the host hardware is not at fault. An agent
that blames pc_0_0's NIC / cable has followed the ticket's misdescription instead
of the evidence.

[FIX]
Bring pc_0_0's access link back up: on leaf_router_0_0, `ip link set eth2 up`.
Once eth2 is UP again, pc_0_0 reattaches to its leaf and reaches pc_0_1 across
the fabric. pc_0_0's host NIC / cabling needs no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from pc_0_0, ping pc_0_1 (10.0.1.2) -- fails --
   before drawing any conclusion.
2. Test the host-side cause the ticket asserts: the failure is at leaf_router_0_0's
   access port eth2 (-> pc_0_0), which is DOWN -- the fault is on the leaf's port,
   so the "bad host NIC / cable" premise is false.
3. Localize the down link: on leaf_router_0_0, the host-facing link eth2 is DOWN
   -> pc_0_0 is severed at L1/L2 from its leaf at the leaf's side.
4. Localize to leaf_router_0_0 (access link eth2 down), not the host: the dead
   leaf access port fully explains the total loss of connectivity for pc_0_0;
   reject the host-NIC/cable cause.

[SCORING-AXES]
assert-identifies: leaf_router_0_0
must-identify-link-down: identifies pc_0_0's access link (leaf_router_0_0 eth2) is down, not a host NIC/cable fault
bonus-rules-out-host-nic: notes the down interface is leaf_router_0_0's access port (eth2), not pc_0_0's hardware, rejecting the "bad host NIC/cable" cause
