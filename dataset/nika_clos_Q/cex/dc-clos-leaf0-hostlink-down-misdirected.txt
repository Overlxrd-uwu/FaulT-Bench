[PROMPT-TO-AGENT]
Helpdesk ticket #9103: A user on pc_0_0 (10.0.0.2) reports they lost all
connectivity -- pc_0_0 can't reach pc_0_1 (10.0.1.2) or anything across the
fabric. The team blames the fabric -- they say "spine_router_0_0 has failed,
swap the spine". Please find and confirm the real fault and tell us which
device or link to restart.

[INJECTION]
device: leaf_router_0_0
action: take down pc_0_0's access link (eth2) on leaf_router_0_0
cmd: ip link set eth2 down

[POST-INJECT-CHECK]
leaf_router_0_0   ip -br link show eth2 | grep -c UP  => expect 0
pc_0_0            ping -W2 -c2 10.0.1.2               => expect loss>0

[GROUND-TRUTH]
The real fault is on leaf_router_0_0: pc_0_0's access link -- the host-facing
interface eth2 (leaf_router_0_0 -> pc_0_0) -- is DOWN, so pc_0_0 (10.0.0.2) is
cut off at its own top-of-rack leaf and cannot reach pc_0_1 (10.0.1.2) or
anything beyond. The ticket MISDIRECTS to the fabric / a spine, but the fabric
is healthy: the CLOS fabric is redundant and the OTHER leaf (leaf_router_0_1)
still reaches the fabric normally through both spines, which it could not do if
spine_router_0_0 had failed. The symptom is purely the down access link at
pc_0_0's leaf, not a spine/fabric fault.

The correct diagnosis identifies leaf_router_0_0 (host-facing access link eth2
down) as the faulty device and explicitly EXONERATES spine_router_0_0: the
spines and fabric still carry the other leaf, so the user's "spine has failed"
hypothesis is wrong. An agent that swaps / blames spine_router_0_0 has followed
the ticket's misdirection instead of the evidence.

[FIX]
Bring pc_0_0's access link back up: on leaf_router_0_0, `ip link set eth2 up`.
Once eth2 is UP again, pc_0_0 reattaches to its leaf and reaches pc_0_1 across
the fabric. spine_router_0_0 / the fabric needs no change.

[DIAGNOSTIC-PROCESS]
1. Reproduce on the real path: from pc_0_0, ping pc_0_1 (10.0.1.2) -- fails --
   before drawing any conclusion.
2. Test the spine the ticket blames: spine_router_0_0 is healthy -- the other
   leaf (leaf_router_0_1) still reaches the fabric through both spines, so the
   ticket's "spine has failed" premise is false.
3. Check pc_0_0's own attachment: on leaf_router_0_0, the host-facing link eth2
   (-> pc_0_0) is DOWN -> pc_0_0 is severed at L1/L2 from its leaf.
4. Localize to leaf_router_0_0 (access link eth2 down), not a spine: the dead
   access link fully explains the total loss of connectivity for pc_0_0;
   exonerate spine_router_0_0.

[SCORING-AXES]
assert-identifies: leaf_router_0_0
assert-not-identifies: spine_router_0_0
must-identify-link-down: identifies pc_0_0's access link (leaf_router_0_0 eth2) is down, not a fabric/spine fault
bonus-exonerates-spine: explicitly notes the spines/fabric still carry the other leaf, rejecting the ticket's spine hypothesis
