==================================================
Scenario: dc-clos-spine0-bgpd-down
Topology: dc_clos_bgp
Fault family: routing daemon down (redundancy loss, no user outage)
==================================================

[PROMPT-TO-AGENT]
Monitoring raised a fabric alarm: super_spine_router_0 and BOTH leaf
routers each report their BGP session toward spine_router_0_0 going
down within seconds of each other. No user has complained -- pc_0_0
(10.0.0.2) and pc_0_1 (10.0.1.2) still reach each other -- but the
fabric is now running without its usual redundancy. All of
spine_router_0_0's interfaces still show UP. Find what broke.

[INJECTION]
device: spine_router_0_0
action: kill the BGP routing daemon (and watchfrr) on spine_router_0_0
cmd: pkill -9 watchfrr; pkill -9 bgpd

[POST-INJECT-CHECK]
spine_router_0_0   pgrep bgpd              => expect empty
pc_0_0             ping -W2 -c2 10.0.1.2   => expect 0% loss   (still OK -- redundant fabric via spine_router_0_1)

[GROUND-TRUTH]
Affected component: spine_router_0_0 bgpd
Mechanism: spine_router_0_0 (AS 65100) peers with super_spine_router_0
  (172.16.0.0, AS 65000), leaf_router_0_0 (172.16.0.5, AS 65200) and
  leaf_router_0_1 (172.16.0.7, AS 65201). Killing bgpd tears down all
  three sessions at once (the peers see the TCP session close and fall
  to Idle/Active). The CLOS fabric is redundant: both leaves still peer
  with spine_router_0_1, so 10.0.0.0/24 and 10.0.1.0/24 stay reachable
  via the other spine and users see at most a brief blip. The impact is
  loss of path redundancy, not an outage.
Localization: spine_router_0_0
Root cause: bgpd not running on spine_router_0_0
Fix: restart FRR on spine_router_0_0 (`service frr restart`) -- the
  config persists in /etc/frr/frr.conf, so the restart restores all
  three sessions.

Observable note: bgpd is killed together with watchfrr (its watchdog),
so nothing respawns it (this kill pattern is lab-verified on this
fabric's leaf routers, 2026-07-03; the spines run the same image and
FRR config layout). vtysh remains responsive via zebra,
`show running-config` on spine_router_0_0 simply contains NO
`router bgp` section, and `show daemons` no longer lists bgpd. An agent
may therefore correctly describe this fault as "the bgp configuration
is missing/empty on spine_router_0_0" -- that is the same fault observed
at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`service frr restart` on spine_router_0_0. The persistent
/etc/frr/frr.conf brings bgpd back with its full neighbor configuration;
the sessions to the super-spine and both leaves re-establish and the
fabric regains its second spine path.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom pattern: three independent devices (the super-spine
   and both leaves) lost their session to the SAME peer, spine_router_0_0,
   simultaneously -- that points at spine_router_0_0 itself, not at any
   single link.
2. Verify there is no user outage: pc_0_0 still reaches pc_0_1 -- the
   fabric converged onto spine_router_0_1, consistent with a redundant
   CLOS losing one spine.
3. Check layer 1/2 on spine_router_0_0: eth0/eth1/eth2 are all UP with
   no carrier transitions -- not a link fault.
4. Check the daemon on spine_router_0_0: `pgrep bgpd` is empty (and
   `show daemons` no longer lists bgpd) -- the BGP daemon is dead while
   zebra is still running.
5. Localize to spine_router_0_0 bgpd: one dead daemon explains all three
   simultaneous session drops and the intact data plane; exonerate the
   links, the leaves and the super-spine.
