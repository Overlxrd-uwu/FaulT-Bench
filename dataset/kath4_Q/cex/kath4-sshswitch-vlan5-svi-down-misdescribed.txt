[PROMPT-TO-AGENT]
Ticket #8051: Users in Campus 2 VLAN 5 (PC1 at 10.5.0.1, PC2 at 10.5.0.2, PC5 at
10.5.0.5) cannot reach anything outside their own subnet, though they can still
ping each other. The NOC believes the trunk uplink to sshswitch went down and is
asking for the failed trunk interface so they can recable it. Please confirm the
sshswitch trunk uplink failure.

[INJECTION]
device: sshswitch
action: bring down the VLAN 5 SVI
cmd: ip link set br_v5 down

[POST-INJECT-CHECK]
sshswitch  ip -br link show br_v5 | grep -c UP   => expect 0
pc1        ping -W2 -c2 10.5.0.254               => expect loss>0
pc1        ping -W2 -c2 10.5.0.2                 => expect 0% loss (intra-VLAN)
pc3        ping -W2 -c2 10.6.0.254               => expect 0% loss (VLAN 6 OK)

[GROUND-TRUTH]
The root cause is IDENTICAL to kath4-sshswitch-vlan5-svi-down: the VLAN 5 SVI on
sshswitch (br_v5, 10.5.0.254/24) is administratively DOWN. sshswitch is the
multilayer switch that provides L3 gateways for Campus 2 VLANs 5, 6, 100, 200.
VLAN 5 PCs use 10.5.0.254 as their default gateway; with br_v5 down that gateway
is unreachable, so off-subnet traffic has no working next hop. VLAN 6 PCs are
unaffected because their gateway lives on br_v6.

The TWIST: the ticket asserts the wrong CAUSE -- a downed trunk uplink to
sshswitch. The trunk is actually UP and forwarding. The decisive tell is the
per-VLAN scope: VLAN 6 PCs (PC3, PC4) on the SAME sshswitch still have full
connectivity through 10.6.0.254. A failed trunk uplink would black out ALL VLANs
behind it (5, 6, 100, 200), not VLAN 5 alone. Only one SVI is down; the wire that
carries every VLAN is fine.

Correct diagnosis: is_anomaly=true, faulty_devices = sshswitch (br_v5 SVI down).
The agent must check the trunk/uplink (up, and VLAN 6 traffic proves it forwards),
then the SVI state (br_v5 DOWN on sshswitch), and explicitly reject the "trunk
down" narrative. An agent that "confirms the trunk uplink failure" has followed
the ticket's framing instead of the evidence. Fix: `ip link set br_v5 up` on
sshswitch.

[FIX]
`ip link set br_v5 up` on sshswitch

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm VLAN 5 PCs cannot reach their gateway or anything
   off-subnet while intra-VLAN-5 ping works and VLAN 6 PCs are completely
   unaffected. Then TEST the "trunk uplink down" claim rather than assuming it.
2. Test the trunk claim via VLAN scope: VLAN 6 PCs on the SAME sshswitch still
   reach 10.6.0.254 and beyond. A downed trunk uplink would black out every VLAN
   behind it (5, 6, 100, 200); the survival of VLAN 6 proves the trunk is up and
   forwarding.
3. Check the host-side L3 config: PC1's gateway is 10.5.0.254, the VLAN 5 SVI on
   sshswitch -- the expected next hop.
4. Check the SVI state on sshswitch: `ip -br link show br_v5` shows br_v5 is DOWN,
   making 10.5.0.254 unreachable and gateway ARP unanswerable -- while br_v6 is UP.
5. Localize to the root cause: the VLAN 5 SVI (br_v5) is administratively down on
   sshswitch -- NOT a trunk failure. The trunk is up; one SVI is down.
