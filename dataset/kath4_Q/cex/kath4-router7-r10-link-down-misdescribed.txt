[GROUND-TRUTH]
The root cause is IDENTICAL to kath4-router7-r10-link-down: router7's eth3 (the
router7<->router10 backbone link, 10.0.0.0/24) is DOWN. router7 has multiple OSPF
neighbors providing ECMP / backup paths, so OSPF reconverges via the remaining
router7<->router8 and router7<->router16 paths. Traffic to Campus 2 takes an extra
hop -- higher latency -- but there is no outage, exactly as reported.

The TWIST: the ticket asserts the wrong CAUSE -- a crashed ospfd on router7.
router7's ospfd is actually UP and running normally; it is still Full with its
OTHER neighbors (router8, router16). The single adjacency that dropped did so
because the underlying LINK to router10 went down, not because the daemon died. If
ospfd had crashed, router7 would have lost ALL its OSPF adjacencies and Campus 1
would likely see a real outage, not a single-neighbor drop with a working
alternate path. Restarting ospfd would not bring eth3 back up.

Correct diagnosis: is_anomaly=true, faulty_devices = router7 (eth3 /
router7<->router10 link down). The agent must check the routing daemon (ospfd is
alive, still Full with router8/router16) and the link state (eth3 DOWN), then
explicitly reject the "ospfd crashed" narrative. An agent that "confirms the
router7 ospfd crash" has followed the ticket's framing instead of the evidence.
Fix: `ip link set eth3 up` on router7.

[FIX]
`ip link set eth3 up` on router7

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm there is no full outage -- traffic to Campus 2 still
   succeeds via an alternate path -- but some users see higher latency and router7
   logged ONE OSPF neighbor going down. Then TEST the "ospfd crashed" claim rather
   than assuming it.
2. Check the routing daemon on router7: `pgrep ospfd` is non-empty and
   `show ip ospf neighbor` still shows router7 Full with its other neighbors
   (router8, router16). ospfd is alive -- a crash would have dropped ALL
   adjacencies, not one.
3. Check interface/link state on router7: `ip -br link show` shows eth3 is DOWN.
   A single dead link, with a live daemon, explains a single dropped adjacency.
4. Correlate route convergence: the lost adjacency is specifically the router10
   neighbor; OSPF reconverged via router7<->router8 and router7<->router16, so
   traffic takes an extra hop -- the latency increase without an outage.
5. Localize to the root cause: physical link router7 eth3 (router7<->router10,
   10.0.0.0/24) is down -- NOT an ospfd crash. The daemon is up; the wire is the
   fault.
