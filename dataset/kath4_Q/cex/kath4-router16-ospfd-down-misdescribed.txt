==================================================
Scenario: kath4-router16-ospfd-down-misdescribed
Topology: Kath4
Fault family: routing daemon down (misdescribed cause)
==================================================

[PROMPT-TO-AGENT]
Ticket #8027: After a maintenance event, all Campus 1 PCs (PC5-PC14) lost
reachability to Campus 2 and the backbone, while intra-Campus-1 traffic still
works. The team believes the link between mswitch0 and router16 went down or was
unplugged during the maintenance. Please confirm the mswitch0<->router16 link
failure and identify the down interface.

[INJECTION]
device: router16
action: kill ospfd (kill watchfrr first so FRR does not respawn it)
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
router16  pgrep ospfd                                       => expect empty
pc5       ping -W2 -c2 10.5.0.1                              => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath4-router16-ospfd-down: ospfd is dead on
router16, the L3 edge between Campus 1 (mswitch0) and the backbone. With ospfd
stopped, Campus 1's uplink no longer advertises or learns, so Campus 1 loses
off-campus reachability while intra-Campus-1 traffic continues.

The TWIST: the ticket asserts the wrong CAUSE -- a downed mswitch0<->router16
link. The link is actually UP and forwarding; nothing physical failed. The "lost
off-campus reachability" symptom is real, but the narrated cause (a
maintenance-window link failure) is a red herring -- the routing daemon stopped,
the wire did not.

Correct diagnosis: is_anomaly=true, faulty_devices = router16 (ospfd not running).
The agent must check Layer 1/2 (the mswitch0<->router16 link is up), then the
routing daemon (ospfd dead on router16), and explicitly reject the "link down"
narrative. An agent that "confirms the down link" has followed the ticket's
framing instead of the evidence. Fix: restart FRR AND re-apply the `router ospf` configuration on router16 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on router16" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
Restart FRR / the ospfd daemon on router16 (e.g. `/etc/init.d/frr restart` on
router16). Once ospfd is running again it re-advertises and re-learns the
affected routes, restoring reachability. (The ticket misattributes the fault;
the remediation targets router16.)

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ospfd back CONFIG-LESS and the ospf service stays broken. The complete remediation is to (re)start FRR/ospfd AND re-apply the `router ospf` configuration (network statements) on router16. A proposal that restores the missing ospf configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm Campus 1 lost off-campus reachability while
   intra-Campus-1 works -- then TEST the ticket's "link down" claim rather than
   assuming it.
2. Layer 1/2 first: check the mswitch0<->router16 link and router16's interfaces
   -- they are UP and forwarding. The narrated physical failure did not happen.
3. Check the routing daemon: `pgrep ospfd` on router16 is empty -- ospfd is dead.
   A live link with a dead daemon produces exactly this symptom.
4. Confirm propagation: Campus 1 prefixes are withdrawn beyond router16 and the
   mswitch0<->router16 OSPF adjacency is no longer Full because router16 stopped
   sending hellos.
5. Localize to the root cause: ospfd not running on router16 -- NOT a link
   failure. The link is up; the routing daemon is the fault.
