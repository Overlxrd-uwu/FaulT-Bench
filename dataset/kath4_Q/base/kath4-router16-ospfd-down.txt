==================================================
Scenario: kath4-router16-ospfd-down
Topology: Kath4
Fault family: routing daemon down (Campus-1 edge)
==================================================

[PROMPT-TO-AGENT]
After a maintenance event on router16, all Campus 1 PCs
(PC5-14) report intermittent reachability to Campus 2 and the
backbone. The mswitch0 SVI gateways still respond, but anything
beyond router16 is unreachable. Diagnose.

[INJECTION]
device: router16
action: kill ospfd
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
router16  pgrep ospfd                                          => expect empty
pc5       ping -W2 -c2 10.5.0.1                                => expect loss>0

[GROUND-TRUTH]
Affected component: router16 ospfd
Mechanism: router16 is the L3 edge between mswitch0 (Campus 1
  multilayer switch) and the backbone (router7/router8/etc.).
  With router16's ospfd dead, mswitch0 loses its OSPF
  neighbor for the backbone direction; Campus 1's only
  uplink stops advertising and learning. Inside Campus 1
  routing continues (mswitch0 ↔ access switches) but no
  off-campus traffic.
Localization: router16
Root cause: ospfd not running on router16
Fix: restart FRR AND re-apply the `router ospf` configuration on router16 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on router16" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on router16

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ospfd back CONFIG-LESS and the ospf service stays broken. The complete remediation is to (re)start FRR/ospfd AND re-apply the `router ospf` configuration (network statements) on router16. A proposal that restores the missing ospf configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm the SVI gateways on mswitch0 still
   respond (intra-Campus-1 intact) but everything beyond — the backbone
   and Campus 2 — is unreachable from all Campus 1 PCs.
2. Inspect the routing table on mswitch0: check for a default/backbone
   route; it should be absent, pointing to a lost OSPF adjacency in
   the backbone direction.
3. Check the OSPF neighbor state on mswitch0: confirm the adjacency to
   router16 is down (not Full), identifying router16 as the boundary
   that stopped peering.
4. Check the routing daemon on router16: run `pgrep ospfd` — the process
   is absent, confirming ospfd is dead rather than a link failure or
   config issue.
5. Localize to the lowest-layer root cause: ospfd not running on
   router16, ruling out a physical link cut or configuration change
   (config is intact; only the daemon crashed).
