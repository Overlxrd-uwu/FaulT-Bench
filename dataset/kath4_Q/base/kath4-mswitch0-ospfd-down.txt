==================================================
Scenario: kath4-mswitch0-ospfd-down
Topology: Kath4
Fault family: routing daemon down (multilayer switch)
==================================================

[PROMPT-TO-AGENT]
All Campus 1 PCs (PC5-14) report Campus 2 (10.5.0.x, 10.6.0.x)
is unreachable. Intra-Campus-1 traffic still works. Campus 2
hosts can still reach each other internally. Find the failure
between the campuses.

[INJECTION]
device: mswitch0
action: kill ospfd
cmd: pkill -9 watchfrr; pkill -9 ospfd

[POST-INJECT-CHECK]
mswitch0  pgrep ospfd                                          => expect empty
pc5       ping -W2 -c2 10.5.0.1                                => expect loss>0

[GROUND-TRUTH]
Affected component: mswitch0 ospfd
Mechanism: mswitch0 is Campus 1's multilayer switch — it owns
  the L3 gateways for VLAN 10/20/30 (172.16.10/20/30.254)
  and runs OSPF to advertise these subnets into the backbone.
  Without ospfd, Campus 1 prefixes age out of router16, router7,
  and onward. Campus 2 still has routes intact (their
  advertiser sshswitch/router17 is unaffected) but Campus 1
  becomes invisible.
Localization: mswitch0
Root cause: ospfd not running on mswitch0
Fix: restart FRR AND re-apply the `router ospf` configuration on mswitch0 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ospfd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router ospf` section, and `show daemons` no longer lists ospfd. An agent may therefore correctly describe this fault as "the ospf configuration is missing/empty on mswitch0" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on mswitch0

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ospfd back CONFIG-LESS and the ospf service stays broken. The complete remediation is to (re)start FRR/ospfd AND re-apply the `router ospf` configuration (network statements) on mswitch0. A proposal that restores the missing ospf configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm the failure is inter-campus only —
   Campus 1 PCs cannot reach Campus 2 (10.5.0.x, 10.6.0.x) but
   intra-Campus-1 traffic works; Campus 2 is internally fine.
2. Inspect routing tables: check router16 and router7 for Campus 1
   prefixes (172.16.10/20/30.0/24) — they should be absent or aged out.
3. Check the OSPF neighbor state: on router16, confirm the adjacency
   to mswitch0 is gone (not Full), establishing that mswitch0 has
   stopped sending OSPF hellos.
4. Check the routing daemon on mswitch0: run `pgrep ospfd` — the
   process is absent, confirming ospfd is dead rather than a link or
   config change.
5. Localize to the lowest-layer root cause: ospfd not running on
   mswitch0, ruling out a physical link failure or OSPF misconfiguration
   (config is intact, the daemon itself crashed).
