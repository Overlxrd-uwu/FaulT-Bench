==================================================
Scenario: kath4-switch1-pc5-wrong-vlan
Topology: Kath4
Fault family: access port in wrong VLAN
==================================================

[PROMPT-TO-AGENT]
PC5 in Campus 1 reports its default gateway (172.16.10.254)
became unreachable, even though PC6/PC7/PC8 on the same switch
work fine. PC5 still gets link, ARP for its own subnet times
out for everyone except itself. What's wrong with PC5's switch
port?

[INJECTION]
device: switch1
action: move PC5's access port (eth2) from br_vlan10 to br_vlan1
  (default VLAN — dead end, no L3)
cmd: |
  ip link set eth2 nomaster
  ip link set eth2 master br_vlan1 2>/dev/null || (ip link add br_vlan1 type bridge; ip link set br_vlan1 up; ip link set eth2 master br_vlan1)

[POST-INJECT-CHECK]
switch1  bridge link show | grep eth2 | grep -c br_vlan10  => expect 0
pc5      ping -W2 -c2 172.16.10.254                        => expect loss>0
pc6      ping -W2 -c2 172.16.10.254                        => expect 0% loss

[GROUND-TRUTH]
Affected component: switch1 eth2 port VLAN membership
Mechanism: switch1's eth2 is the access port for PC5. It was
  moved out of br_vlan10 into br_vlan1 (the unused default
  VLAN). PC5 still sends untagged frames expecting VLAN 10
  semantics, but switch1 now bridges them into VLAN 1 — a
  L2 broadcast domain with no router attached. ARP for the
  gateway gets no reply. Other hosts on br_vlan10 (eth3-5)
  are unaffected.
Localization: switch1 (eth2 port VLAN assignment)
Root cause: access port eth2 moved from VLAN 10 to VLAN 1 on switch1
Fix: `ip link set eth2 master br_vlan10` on switch1

[FIX]
`ip link set eth2 master br_vlan10` on switch1

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm only PC5 is affected — PC6/PC7/PC8 on
   the same switch can still reach 172.16.10.254 — and PC5 cannot ARP
   the gateway, ruling out a host IP misconfiguration and pointing to
   a port-level L2 issue.
2. Check the host-side L3 config: verify PC5's IP, subnet, and gateway
   are correct for VLAN 10 (172.16.10.0/24), eliminating a host
   misconfiguration as the cause.
3. Check switch1 port VLAN membership: run `bridge link show` on
   switch1 — eth2 is a member of br_vlan1 (not br_vlan10), confirming
   the access port was moved to the wrong VLAN.
4. Confirm the L2 dead-end: establish that br_vlan1 / VLAN 1 has no
   L3 router attached, so ARP for 172.16.10.254 gets no reply on that
   broadcast domain.
5. Localize to the lowest-layer root cause: eth2 on switch1 is assigned
   to VLAN 1 instead of VLAN 10, ruling out a PC misconfiguration, an
   SVI failure on mswitch0, or a trunk issue.
