==================================================
Scenario: kath2-router0-wrong-static
Topology: Kath2
Fault family: misconfigured static route
==================================================

[PROMPT-TO-AGENT]
After an admin added a "temporary backup route" on router0,
IT and CS users report Server Room (1.0.0.x) is unreachable
but Internet Lab (128.168.0.x) works fine. Both used to work.
Diagnose.

[INJECTION]
device: router0
action: add a black-hole static for the Server Room prefix
cmd: ip route add 1.0.0.0/8 via 127.0.0.1

[POST-INJECT-CHECK]
router0  ip route show 1.0.0.0/8 | grep -c "127.0.0.1" => expect 1
it_hod   ping -W2 -c2 1.0.0.5                          => expect loss>0
it_hod   ping -W2 -c2 128.168.0.2                      => expect 0% loss

[GROUND-TRUTH]
Affected component: router0 routing table — static route to
  1.0.0.0/8 via 127.0.0.1
Mechanism: Linux prefers static routes over RIP-learned routes
  (admin distance / route metric). The new static for 1.0.0.0/8
  points at the loopback, which silently drops the packets.
  128.168.0.0/16 still uses the RIP-learned route via 10.10.0.2.
Localization: router0
Root cause: incorrect static route `1.0.0.0/8 via 127.0.0.1`
Fix: `ip route del 1.0.0.0/8 via 127.0.0.1` (RIP-learned
  route reinstalls automatically)

[FIX]
`ip route del 1.0.0.0/8 via 127.0.0.1` (RIP-learned
  route reinstalls automatically)

[DIAGNOSTIC-PROCESS]
1. Scope the failing path: confirm IT/CS hosts cannot reach 1.0.0.x while
   128.168.0.x remains reachable from the same hosts. The selective failure
   points to a route-level problem specific to the 1.0.0.0/8 prefix on router0.
2. Inspect router0's routing table: run `ip route show 1.0.0.0/8` — a static
   entry via 127.0.0.1 (loopback) is present, overriding the RIP-learned route
   via 10.10.0.2.
3. Confirm the blackhole mechanism: the static route has lower administrative
   distance than RIP so Linux prefers it; packets for 1.0.0.x are forwarded to
   127.0.0.1 and silently dropped. The 128.168.0.0/16 prefix has no competing
   static, so it still uses the RIP-learned nexthop and works.
4. Localize to the incorrect static route on router0: rule out ripd being down
   (128.168.0.x still works via RIP) and rule out a link failure (interfaces
   are up and other prefixes route correctly).
