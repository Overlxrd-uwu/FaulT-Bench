==================================================
Scenario: kath2-pc1-wrong-netmask
Topology: Kath2
Fault family: host misconfig (wrong subnet mask)
==================================================

[PROMPT-TO-AGENT]
pc1 in the Server Room (was 1.0.0.5) reports it cannot reach
its gateway 1.0.0.1 or anything else. Other devices in the
Server Room (none in this lab) would be unaffected. pc1 was
working before a maintenance task. Other zones unaffected.
What's wrong with pc1 specifically?

[INJECTION]
device: pc1
action: replace /8 mask with /30 (too narrow — gateway 1.0.0.1 falls
  outside 1.0.0.4/30, so the default route cannot be installed and
  pc1 is genuinely isolated)
cmd: |
  ip addr flush dev eth0
  ip addr add 1.0.0.5/30 dev eth0
  ip route add default via 1.0.0.1 2>/dev/null || true

[POST-INJECT-CHECK]
pc1  ip -4 -br addr show eth0 | grep -c "1.0.0.5/30" => expect 1
pc1  ping -c 2 -W 2 1.0.0.1 >/dev/null 2>&1; echo $? => expect 2

[GROUND-TRUTH]
Affected component: pc1 IP/netmask configuration
Mechanism: Server Room subnet is 1.0.0.0/8 (router2's eth0
  has 1.0.0.1/8). pc1 was configured with /30 instead of /8,
  confining it to 1.0.0.4/30 (hosts .5-.6 only). The gateway
  1.0.0.1 is OUTSIDE that range: the kernel rejects
  `default via 1.0.0.1` (nexthop unreachable), pc1 ends up
  with no default route and cannot even ARP the gateway —
  it is cut off from everything beyond its own /30.
Localization: pc1
Root cause: pc1 netmask set to /30 instead of /8 (gateway
  excluded from the local subnet; default route uninstallable)
Fix: restore pc1's mask and default route —
  `ip addr flush dev eth0 && ip addr add 1.0.0.5/8 dev eth0
   && ip route add default via 1.0.0.1`

[FIX]
restore pc1's mask and default route — `ip addr flush dev eth0 && ip addr add 1.0.0.5/8 dev eth0 && ip route add default via 1.0.0.1`

[DIAGNOSTIC-PROCESS]
1. Scope to pc1: confirm pc1 cannot reach its gateway 1.0.0.1 or remote hosts,
   while no other host in the topology is affected.
2. Inspect pc1's addressing: run `ip -4 -br addr show eth0` — the mask shows
   /30 instead of the expected /8, and `ip route` shows no default route.
3. Compare against the subnet: the Server Room gateway 1.0.0.1 sits at router2's
   eth0 with a /8 mask; pc1's /30 confines it to 1.0.0.4/30, which excludes the
   gateway entirely — the kernel cannot install `default via 1.0.0.1`, so pc1
   has no path off its own /30.
4. Localize to pc1's misconfigured netmask: no routing daemon, no link failure —
   the fault is entirely on the host. Rule out gateway misconfiguration by
   verifying router2's interface has the correct /8.
