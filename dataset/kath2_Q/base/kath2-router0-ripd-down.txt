==================================================
Scenario: kath2-router0-ripd-down
Topology: Kath2
Fault family: routing daemon down
==================================================

[PROMPT-TO-AGENT]
A user on the CS LAB 1 PC (192.168.2.3) reports they cannot reach
the Server Room (1.0.0.x) or the Internet Lab (128.168.0.x). The
IT Department PCs are also affected. Other zones (Office, Principle,
Internet Lab itself) can still reach each other. What's wrong?

[INJECTION]
device: router0
action: kill ripd
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router0  pgrep ripd                                 => expect empty
cs_lab1  ping -W2 -c2 128.168.0.1                   => expect loss>0

[GROUND-TRUTH]
Affected component: router0 ripd daemon
Mechanism: router0 is the only L3 hop between IT Dept
  (192.168.1.0/24), CS Dept (192.168.2.0/24), and the rest
  of the network (reached via Serial2/0 to router1). When
  ripd dies on router0, router1 ages out the 192.168.1.0/24
  and 192.168.2.0/24 prefixes, and router0 itself stops
  learning the 1.0.0.0/8 / 128.168.0.0/16 / 192.168.3.0/24
  / 192.168.4.0/24 prefixes from router1. IT + CS PCs become
  isolated from everything beyond router0.
Localization: router0
Root cause: RIP routing daemon (ripd) not running on router0
Fix: restart FRR AND re-apply the `router rip` configuration on router0 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router0" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
Restart FRR / the ripd daemon on router0 (e.g. `/etc/init.d/frr restart` on
router0). Once ripd is running again it re-learns the remote prefixes and
re-advertises 192.168.1.0/24 and 192.168.2.0/24, restoring IT Dept and CS Dept
reachability.

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router0. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom cluster: confirm IT Dept (192.168.1.0/24) and CS Dept
   (192.168.2.0/24) cannot reach Server Room and Internet Lab, while Office,
   Principle, and Internet Lab itself can still reach each other. This isolates
   the fault to the path through router0.
2. Inspect the routing table: on router0 check `show ip route` via vtysh — RIP
   routes for 1.0.0.0/8, 128.168.0.0/16, 192.168.3.0/24, and 192.168.4.0/24
   should be missing. On router1, check that 192.168.1.0/24 and 192.168.2.0/24
   have been aged out.
3. Check RIP adjacency: verify router0 has no RIP neighbors / no updates are
   being exchanged, narrowing the cause to router0's RIP control plane.
4. Check daemon state: run `pgrep ripd` on router0 — the process is absent.
5. Localize to router0's ripd: the daemon crash explains both the missing learned
   routes and the withdrawn IT/CS advertisements. Rule out a link failure by
   confirming router0's interfaces are up.
