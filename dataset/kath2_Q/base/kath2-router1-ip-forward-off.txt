==================================================
Scenario: kath2-router1-ip-forward-off
Topology: Kath2
Fault family: ip_forward disabled (silent transit failure)
==================================================

[PROMPT-TO-AGENT]
IT and CS Dept users report they cannot reach Server Room or
Internet Lab. router0 and router2 both report RIP routes intact
and can ping each other's interfaces directly. office_pc (on
router1's own LAN) can still ping its gateway 192.168.3.1, but it
too cannot reach the Server Room. What breaks transit through
router1?

[INJECTION]
device: router1
action: drop all transit forwarding on router1 (net.ipv4.ip_forward is not writable from the exec context, so use the iptables equivalent: a FORWARD-chain drop)
cmd: iptables -A FORWARD -j DROP

[POST-INJECT-CHECK]
it_hod    ping -W2 -c2 1.0.0.5                  => expect loss>0
office_pc ping -W2 -c2 192.168.3.1             => expect 0% loss

[GROUND-TRUTH]
Affected component: router1 packet forwarding (FORWARD chain)
Mechanism: A FORWARD-chain DROP rule makes router1 drop every
  packet it would route BETWEEN interfaces (transit). Transit
  traffic (it_hod -> router0 -> router1 -> router2 -> pc1) is
  dropped at router1, and office_pc -> Server Room is dropped
  too (it is also transit). Only traffic to router1's OWN
  interfaces still works -- office_pc can still ping its gateway
  192.168.3.1 -- which is the tell that router1 is up but not
  forwarding. RIP keeps running because its sockets are local,
  not forwarded. (This is the iptables equivalent of
  net.ipv4.ip_forward=0, used because that sysctl is not writable
  from the exec context.)
Localization: router1
Root cause: a FORWARD-chain DROP rule on router1 stops transit
  forwarding (equivalent to ip_forward disabled)
Fix: `iptables -D FORWARD -j DROP` on router1 (re-enable forwarding)

[FIX]
`iptables -D FORWARD -j DROP` on router1 (re-enable forwarding)

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm IT/CS hosts cannot reach Server Room and Internet
   Lab, while office_pc (on router1's own LAN segment) CAN reach those targets.
   This asymmetry points to a forwarding issue on the transit device, not a
   routing-table or link problem.
2. Verify L1/L2 and routing are healthy: check that router1's interfaces are
   up, RIP routes are intact on router0/router2, and the issue is not a missing
   prefix.
3. Check IP forwarding state: run `sysctl -n net.ipv4.ip_forward` on router1 —
   returns 0, meaning the kernel will not route between interfaces.
4. Confirm the transit-vs-local distinction: traffic that originates or
   terminates on router1 itself (office_pc's gateway is router1) bypasses the
   forwarding path and works; transit traffic (IT/CS -> router0 -> router1 ->
   router2) is dropped by the kernel.
5. Localize to router1 ip_forward=0: rule out a routing-daemon crash (RIP is
   still running) and a link failure (all interfaces are up).
