==================================================
Scenario: kath2-router2-ripd-down
Topology: Kath2
Fault family: routing daemon down
==================================================

[PROMPT-TO-AGENT]
Server Room PC (1.0.0.5) and all Internet Lab PCs (128.168.0.x)
report no inbound connectivity from IT Dept, CS Dept, Other or
Principle zones. Outbound from Server Room/Internet Lab also
appears broken — they cannot reach 192.168.x.x. Inside their
own zones traffic still flows. Identify.

[INJECTION]
device: router2
action: kill ripd
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router2  pgrep ripd                                       => expect empty
it_hod   ping -W2 -c2 1.0.0.5                             => expect loss>0

[GROUND-TRUTH]
Affected component: router2 ripd daemon
Mechanism: router2 is the only L3 path between the rest of
  the network and the Server Room (1.0.0.0/8) + Internet Lab
  (128.168.0.0/16). When ripd dies, router2 stops advertising
  its connected networks via RIP, router1 ages out those
  prefixes, and router2 itself loses learned routes back to
  the 192.168.x.x side. Both directions break.
Localization: router2
Root cause: ripd not running on router2
Fix: restart FRR AND re-apply the `router rip` configuration on router2 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router2" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
`/etc/init.d/frr restart` on router2

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router2. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm bidirectional failure — hosts in all 192.168.x.x
   zones cannot reach Server Room/Internet Lab, AND pc1/Internet Lab hosts
   cannot reach the 192.168.x.x zones. Intra-zone traffic within each side
   still works. This bilateral isolation points to router2's RIP control plane.
2. Inspect the routing table on router1: check that 1.0.0.0/8 and
   128.168.0.0/16 prefixes have been aged out, confirming router2 stopped
   advertising them.
3. Check RIP adjacency: verify router2 has no active RIP neighbors, narrowing
   the fault to router2's RIP daemon.
4. Check daemon state: run `pgrep ripd` on router2 — the process is absent.
   Router2 also lost RIP-learned routes for 192.168.x.x (reverse direction),
   explaining why outbound from Server Room/Internet Lab also fails.
5. Localize to router2's ripd: rule out a link failure by confirming router2's
   eth2 is up; the daemon crash alone explains both advertisement withdrawal and
   loss of learned routes.
