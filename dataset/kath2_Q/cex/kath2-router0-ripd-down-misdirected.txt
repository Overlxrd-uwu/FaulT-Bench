Scenario: kath2-router0-ripd-down-misdirected
Topology: Kath2
Fault family: routing daemon down (misdirected prompt)

[PROMPT-TO-AGENT]
Office and Principle Room users opened ticket #4490: they can no longer reach
the CS and IT department hosts (192.168.1.0/24, 192.168.2.0/24). Their network
team is convinced the problem is on router1 -- specifically that the router1
WAN uplink is dropping their traffic to those departments. Please confirm the
router1 uplink fault and identify the affected interface.

[INJECTION]
device: router0
action: kill ripd
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router0  pgrep ripd                                 => expect empty
cs_lab1  ping -W2 -c2 128.168.0.1                   => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath2-router0-ripd-down: ripd is dead on
router0. router0 is the only L3 hop between IT (192.168.1.0/24), CS
(192.168.2.0/24) and the rest of the network (via Serial to router1). With
ripd down, router1 ages out 192.168.1.0/24 and 192.168.2.0/24, and router0
stops learning the far prefixes -- so Office/Principle <-> CS/IT traffic breaks.

The TWIST: the user report blames router1's WAN uplink. router1 is HEALTHY --
its ripd is running, its WAN uplinks (wan_r0_r1, wan_r1_r2) are up, and it is
simply aging out prefixes it no longer hears advertised from router0. The
symptom Office sees (can't reach CS/IT) is real, but the accusation is wrong:
it is first-hop bias toward the users' own gateway.

Correct diagnosis: is_anomaly=true, faulty_devices = router0 (ripd not
running). The agent must localise from evidence -- router0's dead ripd and the
withdrawn RIP routes -- and explicitly NOT pin the fault on router1 despite the
prompt. An agent that "confirms" the router1 uplink fault the ticket asserts
has followed the accusation instead of the evidence. Fix: restart FRR AND re-apply the `router rip` configuration on router0 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router0" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
Restart FRR / the ripd daemon on router0 (e.g. `/etc/init.d/frr restart` on
router0). Once ripd is running again it re-advertises and re-learns the
affected routes, restoring reachability. (The ticket misattributes the fault;
the remediation targets router0.)

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router0. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: verify that Office/Principle hosts cannot reach
   192.168.1.0/24 and 192.168.2.0/24 (IT/CS) — confirm the symptom is real
   before accepting the ticket's router1 hypothesis.
2. Check router1 first (as accused): verify router1's ripd is running, its WAN
   uplinks (wan_r0_r1, wan_r1_r2) are up, and it is forwarding. If router1 is
   healthy, the accusation is wrong — follow the evidence instead.
3. Check the RIP routing table: on router1 note that 192.168.1.0/24 and
   192.168.2.0/24 are missing — these are prefixes advertised only by router0.
4. Inspect router0: check pgrep ripd — the daemon is dead. With ripd down,
   router0 stops advertising those prefixes and stops learning remote ones.
5. Localize to the root cause: router0's ripd not running; router1 is merely
   aging out prefixes it no longer hears from router0, not the cause of the fault.
