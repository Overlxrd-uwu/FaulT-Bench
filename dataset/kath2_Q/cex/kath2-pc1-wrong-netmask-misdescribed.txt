[GROUND-TRUTH]
The root cause is IDENTICAL to kath2-pc1-wrong-netmask: pc1's own interface
netmask is wrong. The Server Room subnet is 1.0.0.0/8 (router2's eth0 is
1.0.0.1/8), but pc1 was reconfigured with 1.0.0.5/30. The /30 puts pc1 in
1.0.0.4/30 (hosts .5-.6 only), which does NOT contain the gateway 1.0.0.1:
the kernel rejects `default via 1.0.0.1` (nexthop unreachable), pc1 has no
route beyond 1.0.0.4/30, and it cannot even ARP the gateway. The fault lives
entirely in pc1's host configuration.

The TWIST: the ticket asserts the wrong CAUSE -- a misconfigured gateway
router2. router2 is FINE -- its eth0 still carries the correct 1.0.0.1/8, ripd
is running, it advertises 1.0.0.0/8 normally, and it has no per-host filter
against pc1. Nothing changed on router2; the change was made on pc1's own
interface. The symptom (pc1 isolated) is real, but the narrated cause points at
the gateway when the misconfiguration is host-side. Because pc1 is the only
device that lost connectivity while everything else in the topology is healthy,
the evidence localises to pc1, not to a shared gateway.

Correct diagnosis: is_anomaly=true, faulty_devices = pc1 (interface netmask set
to /30 instead of /8). The agent must inspect pc1's addressing, compare it
against the /8 subnet, confirm router2's interface is correct, and explicitly
reject the "gateway router2 misconfigured" narrative. An agent that "confirms
the router2 misconfiguration" has followed the ticket's framing instead of the
evidence. Fix: restore pc1's address and default route --
`ip addr flush dev eth0 && ip addr add 1.0.0.5/8 dev eth0 && ip route add
default via 1.0.0.1`.
