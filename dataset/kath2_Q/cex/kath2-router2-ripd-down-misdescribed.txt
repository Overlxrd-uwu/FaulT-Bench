[PROMPT-TO-AGENT]
Ticket #4512: After last night's maintenance, the Server Room (1.0.0.x) and
Internet Lab (128.168.0.x) lost connectivity to all the 192.168.x.x departments
(and vice versa), while traffic inside each zone still works. The team believes
router2's WAN serial interface (eth2, toward router1) went down or was unplugged
during the maintenance. Please confirm the router2 WAN link failure and identify
the down interface.

[INJECTION]
device: router2
action: kill ripd (kill watchfrr first so FRR does not respawn it)
cmd: pkill -9 watchfrr; pkill -9 ripd

[POST-INJECT-CHECK]
router2  pgrep ripd                                       => expect empty
router2  ip -br link show eth2 | grep -c UP               => expect 1
it_hod   ping -W2 -c2 1.0.0.5                              => expect loss>0

[GROUND-TRUTH]
The root cause is IDENTICAL to kath2-router2-ripd-down: ripd is dead on router2.
router2 is the only L3 path between the rest of the network and the Server Room
(1.0.0.0/8) + Internet Lab (128.168.0.0/16). With ripd stopped, router2 stops
advertising its connected networks, router1 ages out 1.0.0.0/8 and 128.168.0.0/16,
and router2 loses its learned 192.168.x.x routes -- so both directions break while
intra-zone traffic continues.

The TWIST: the ticket asserts the wrong CAUSE -- a downed router2 WAN serial
(eth2). The link is actually UP and forwarding: router2's eth2 is up and its
serial neighbor is reachable; nothing physical failed. The bilateral isolation
symptom is real, but the narrated cause (a maintenance-window link failure) is a
red herring -- the routing daemon stopped, the wire did not.

Correct diagnosis: is_anomaly=true, faulty_devices = router2 (ripd not running).
The agent must check Layer 1/2 (eth2 is UP), then the routing daemon (ripd dead on
router2), and explicitly reject the "WAN link down" narrative. An agent that
"confirms the down uplink" has followed the ticket's framing instead of the
evidence. Fix: restart FRR AND re-apply the `router rip` configuration on router2 (see [FIX] -- a bare restart alone does not restore the vtysh-applied config).

Observable note (lab-verified 2026-07-03): ripd is killed together with watchfrr (its watchdog), so nothing respawns it. vtysh remains responsive via zebra, `show running-config` simply contains NO `router rip` section, and `show daemons` no longer lists ripd. An agent may therefore correctly describe this fault as "the rip configuration is missing/empty on router2" -- that is the same fault observed at the config plane, and must NOT be treated as a wrong root cause.

[FIX]
Restart FRR / the ripd daemon on router2 (e.g. `/etc/init.d/frr restart` on
router2). Once ripd is running again it re-advertises and re-learns the
affected routes, restoring reachability. (The ticket misattributes the fault;
the remediation targets router2.)

NOTE (lab-verified 2026-07-03): this lab applies FRR config via vtysh at boot (there is no /etc/frr/frr.conf), so `/etc/init.d/frr restart` alone brings ripd back CONFIG-LESS and the rip service stays broken. The complete remediation is to (re)start FRR/ripd AND re-apply the `router rip` configuration (network statements) on router2. A proposal that restores the missing rip configuration is a correct fix; a bare daemon restart without restoring the config is incomplete.

[DIAGNOSTIC-PROCESS]
1. Scope the symptom: confirm the bilateral isolation (Server Room/Internet Lab
   <-> 192.168.x.x) while intra-zone works -- then TEST the ticket's "WAN link
   down" claim rather than assuming it.
2. Layer 1/2 first: check router2's WAN interface -- eth2 is UP and forwarding,
   and the serial neighbor is reachable. The narrated physical failure did not
   happen.
3. Check the routing daemon: `pgrep ripd` on router2 is empty -- ripd is dead. A
   live link with a dead daemon produces exactly this symptom.
4. Confirm propagation: from router1, 1.0.0.0/8 and 128.168.0.0/16 have aged out
   of RIP because router2 stopped advertising.
5. Localize to the root cause: ripd not running on router2 -- NOT a link failure.
   The WAN link is up; the routing daemon is the fault.
